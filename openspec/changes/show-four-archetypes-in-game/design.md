## Context

当前评分层已经为每张铁甲候选生成四条 `archetypeImpacts`，但发回 Mod 的 `draft_impact` 只提取自动打击别名；Mod 也只解析每卡一个整数并创建单行标签。奖励签名、候选 ID 校验、固定三卡锚点、字体回退和清理生命周期已经存在，可直接扩展。

## Goals / Non-Goals

**Goals:**

- 将已有四条候选增量完整送到 Mod，并在每张卡上方固定显示四行。
- 保留现有奖励签名和候选校验，防止迟到消息污染新奖励。
- 让旧 Mod 收到新消息时仍至少能读取自动打击单值。

**Non-Goals:**

- 不显示当前牌组四套总分或判断主流派。
- 不做最多两条筛选、原因详情和可展开交互。
- 不删除桌面端已有代码；本变更只确保实际交付不依赖桌面端。

## Decisions

### 1. 在现有 `draft_impact` 每卡对象上追加四套数组

每个候选保持旧 `cardId` 与自动打击 `deltaPoints`，并新增固定四项：

```text
{
  cardId,
  deltaPoints,
  archetypes: [
    { id: "auto_strike", deltaPoints },
    { id: "exhaust", deltaPoints },
    { id: "strength", deltaPoints },
    { id: "block", deltaPoints }
  ]
}
```

保留外层类型与旧单值，可让旧 Mod 忽略新增字段继续显示自动打击；新 Mod 则严格要求四个唯一 ID。相比另建消息类型，这能复用签名、队列和生命周期。

### 2. Mod 使用每卡一个面板和四个固定顺序文本行

每个候选仍只创建一个穿透输入的面板，内部改为四行纵向容器。顺序固定为自动打击、消耗引擎、力量叠加、格挡壁垒；正数绿色、负数红色、零值灰色。相比四个独立浮层，一个面板更容易维持三卡对齐和统一清理。

### 3. 完整校验后原子替换

解析阶段校验候选数量、卡牌 ID、四个流派 ID 唯一性和 `[-100, 100]` 整数范围；任一候选不完整即拒绝整条消息。只有签名与当前奖励相同且所有卡牌 ID 属于当前奖励时才清除并重建标签，避免出现部分新、部分旧的混合状态。

### 4. 直接展示四条，不复用桌面筛选器

协议直接使用评分层已有的完整 `archetypeImpacts`，不调用桌面端“最多两条”选择逻辑。这样游戏内行为符合当前明确需求，也不会把 UI 选择规则误当成评分规则。

## Risks / Trade-offs

- **[风险] 四行高度遮挡卡牌或其他原生 UI** → 使用现有卡牌上方锚点，按视口计算更高但受控的面板，并在实机三卡奖励上验证。
- **[风险] 中英文文本宽度不同** → 使用短名称、居中布局和现有字体替换；中文缺字时整组回退英文。
- **[风险] GameBuddy 与 Mod 版本不同步** → 保留旧自动打击 `deltaPoints`；新 Mod 对缺少四套数组的旧消息不展示不完整面板。

## Migration Plan

1. 先扩展 Node 消息并补充协议测试。
2. 再更新 Mod 解析和四行布局。
3. 构建 Mod，运行 Harness，并用实际三卡奖励验证位置、刷新和点击。
4. 回滚时恢复 Mod 单行读取；新增协议字段可被旧消费者忽略。
