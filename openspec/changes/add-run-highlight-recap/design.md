# Design: GameBuddy 本局复盘完整计划

版本：讨论收敛版 v2＋真实对局迭代。日期：2026-11-09。状态：核心已有本地实现，当前执行4局真实失败记录评测与优化；完成范围见 verification.md 和 iterations/2026-11-09/。

## Context

本功能为玩家提供简短的本局复盘：固定数据条、模型从本局记录中找出的三个重要片段，以及最后一句总结。片段可以是有证据的失误、遗憾、关键选择或高光；按对本局的重要性选取，不限定为正向高光，也不强制好坏配比。伏笔、反差、转折或错失机会能增强复盘价值，例如“低血选择升级，下一场精英阵亡，刚升级的牌一次未用”。

时序日志是共同事实基础。补足每个关键时点的信息，模型就可以寻找许多联系；只有精确归因或反事实需要额外来源/验证。第一版不以完整因果图和全游戏模拟器为前提。

本计划取代本change早期“单次模型在预选候选中写短评”的设计，采用单模型、受控只读工具的查证流程。文中字段、工具、模块和性能预算均为拟议方案；合成示例不是实际战绩。

## Goals / Non-Goals

### Goals

1. 让玩家十几秒看到这局最值得回味的事。
2. 用全局概览与按需查证发现意外、遗憾、套路兑现和有据机会，而不局限于极值。
3. 固定数字准确，负面事实有覆盖证明，结论强度匹配证据。
4. 日志、工具、输出可复现，模型效果与工程行为分开评估。
5. 同一事实源服务复盘，未来可向弹幕/长期记忆提供已验证的短经历。

### Non-Goals

不提供玩家逐回合过程/长报告/回放控制；不做水平评分、全游戏最优求解、整体反事实胜率；不改游戏状态；不在本期部署长期记忆、图数据库或新的通用Agent框架。

## Decisions

### 1. Player Experience

在个人数据单局记录内增加“本局复盘”，采用“固定数据条＋三个重要片段＋一句总结”的结构。正常情况下从本局记录中选择三个不同片段，每张标题≤10字、正文≤40字；最后一句总结≤40字，渲染后正文目标120–220字。记录不足时允许少于三个并简短说明，不虚构片段。数字和名称绑定后再计算长度，不能用截断破坏事实。

本次按用户认可的战报展示更新数字条：顶部交代角色、进阶、总层数/所在幕及结果；游戏计时未验收时明确展示“记录覆盖”，不把日志跨度当实际游玩时长。固定四项为累计输出、实际抗伤、累计受伤、实际恢复。伤害按已确认阵营及实际扣血累计，治疗只接受实际恢复或明确前后生命差，不累加治疗请求量；存在范围缺口时未知不填0。原最高回合实际爆发、最高斩杀、SL继续作为次级已知纪录，口径不变。

画面采用本地生成的高塔、篝火、精灵插画和暗色遮罩；正文保持高对比，不在线加载素材、不展示工程证据。已记录火堆回血/升级次数和明确的上限增长可放在数字下方，范围不冒充完整对局。

文风为“陪玩家打完这局的损友兼战地记者”：懂机制、温和调侃，优先说出选择与后来兑现、反差、险情。火堆风格要比较回血与可用升级、当时生命；事件画像至少结合不同决策中的代价/收益取舍，不推断稳定人格。对瓶中精灵救命允许显式的机制吻合推断：战斗内确认先持有、归零时消失、实际恢复与该版本30%机制吻合、窗口无读档/跨战斗歧义；还可回扣此前明确保留精灵的选择。该关系须标为机制吻合推断，不伪称拥有直接药水来源ID；只有时间相邻不成立。原始记录和全局调查仍供模型发现其他片段，不局限这三种关系。

三个片段从本局记录中查找，可包含：有证据的失误、升级未兑现、核心来迟、资源留到终局、套路终于运转、夸张击杀、险胜反转或经过验证的错失斩杀。优先重要、有本局特色且证据充分的片段，兼顾前后联系；不要求每种类型都出现。同一事件多纪录合并为一个片段，避免三张卡重复。普通经过仅作背景，没有复盘价值时不单独成卡。

页面不展示工具、证据ID、工程解释、时间线或展开战报。保留原有历史列表和终局牌组能力，不自动弹窗打断下一局。生成异步，先展示固定数据条和复盘生成状态，模型查证后呈现三个片段，并根据这些片段生成最后一句总结；无Key或失败时保留本地可核实内容。重新打开直接读缓存。

合成文风示例：

> **升级了，没用上**：24血时升级的那张牌，下一场精英战阵亡前，一次也没打出。
>
> **终于等到，没能量了**：核心牌终于上手，能量却已经在前几张牌里花完。
>
> **有点用力过猛**：小怪只剩10血，却吃到9999点单次结算伤害。

具体文案由各自证据决定：没上手、上手不可用、可用未用必须区分；不能编造玩家动机或自动判断失误。

### 2. Unified Timeline and Evidence

```text
真实游戏事件与关键状态
  → 本地时序事实＋快照＋完整度
  → 有效尝试视图／重载元数据
  → 固定纪录＋全局战斗/选择/对象索引
  → 模型发现候选 → 只读工具查询 → 结构化断言检查
  → 固定数据条＋三个已支持的重要片段＋最后一句总结
```

关键时点是选择前后、动作前和结算后、回合开始结束、战斗开始结束；完整锚点配合增量。先解决时序与状态关联，精确收益归因只在需要时补来源。详细字段及各情境读取路径见data-contract.md。

原始记录保留，默认战绩只取有效尝试；SL事件独立留存。零次事实依赖范围完整、身份可靠和无影响缺口。旧日志缺字段自然降级，不能回填猜测数值。

### 3. Interpretation Levels

| 层级 | 示例 | 证据要求 |
| --- | --- | --- |
| 事实反差 | 升级后阵亡，该牌整场未使用 | 明确事件、对象身份、结果、整场零次证明 |
| 机制联系 | 本回合先耗尽能量，核心上手时无法支付 | 对应时点手牌/动态费用/资源/限制及顺序 |
| 局部反事实 | 当时有一套已验证的斩杀顺序 | 独立受支持计算器及合法行动序列 |
| 全局反事实 | 如果回血，这局必胜 | 本期不支持，不发布 |

故事发生先后可从时序发现；是否为坏选择仍要考虑当时可见信息和机会成本。后续坏抽牌不等于前面操作错。套路使用片段当时的组件/版本和实际触发，不拿终局牌组倒推，不恢复流派分数。

### 4. Investigation Harness

六个工具：get_run_overview、find_events、read_event_window、inspect_subject、get_mechanic_facts、check_claims。边界与参数见harness-and-tools.md。

模型先浏览全局概览和重要选择索引，再按兴趣查对象和连续窗口，提交候选片段及断言，程序核数/身份/范围并允许一次补证。模型可发现未预设奖项的新故事；不得自由增加未验证数字或强因果。

初始最多4轮取证、10次读取、1轮检查修复，整体预算初始90秒；均为待测配置。缺资料允许不下结论，失败保留本地纪录。所有查询绑定当前事实版本，清空、迟到结算或SL替换后旧结果失效。

### 5. Limited Counterfactual Verification

verify_action_sequence属于独立后续能力，只对明确支持的本回合确定机制做纯函数验证。先覆盖合法目标、费用、伤害/格挡和已支持状态；任何未支持触发、随机依赖或规则返回unsupported。

该能力未验收前不允许写“本来一定能赢”。即使验证当回合可斩杀，也不能推演整局必胜。故事发现、固定数字与事实反差可先上线。

### 6. Technical Choices

| 技术 | 选择与原因 |
| --- | --- |
| 采集 | 现有C#/Harmony，增加正确时点的只读捕获与字段质量 |
| 传输 | 现有本机WebSocket与版本化事实信封，保留ACK/去重 |
| 存储 | 现有JSONL＋可靠快照＋可重建索引，保持安装版兼容 |
| 整理与工具 | Node.js纯函数/受控读取，复用现有事实及知识模块 |
| 模型 | 现有已配置服务，新增独立复盘工具交互适配；不更换实时链路 |
| 输出校验 | schema、程序断言、metric/entity绑定；语义部分用评测持续检查 |
| UI | 现有Electron个人数据页，窄IPC传递短回顾 |
| 测试 | node:test、现有Harness、Electron renderer、C# codec与Windows实机 |

当前阶段不引入额外数据库、复杂编排平台或长期记忆依赖。模块位置和接口细节在附录中明确，避免大规模重写。

### 7. Storage, Model Processing and Diagnostics

本地保存原始日志、快照、版本化高光投影及显式工具轨迹；高光始终可由源数据重建。缓存键包含runId、factsRevision、模型/配置、提示/工具/知识版本。

本次用户明确要求模型依据日志查找片段，模型请求会包含当前对局概览、必要局部事件、状态和SL。整库历史、密钥、种子、共享留言不进入请求；相关“仅本地”文案必须准确区分本地保存和模型处理，不增加额外的历史批量发送。

诊断保存请求、显式工具交互、结果/校验/用量与失败原因，不要求完整思考流。固定响应用于工程复现，重新请求用于模型效果评测。

后续长期记忆可消费已支持的故事与证据引用；本期本局画像仅概括已记录的多次选择，不推断稳定人格，也不修改实时推荐策略。

### Real Run Iterations (2026-11-09)

用户授权只以本地4把历史loss且明确结束的对局持续评测、独立子agent审查、修改和重测，每轮保存效果报告与下一轮计划。原始日志只读，派生测试数据放本地.runtime，报告放本change的iterations/2026-11-09/。不再生成100层合成对局；既有工程边界测试保留。4局均为开发样本，不能声称独立留出集或玩家人工盲评。

旧日志的正向事件、已知状态和前后反差仍可用于故事；缺失阵营/动作关联/唯一实例/入手和致死信息不可按相邻关系猜补。历史loss只说明失败归档；game_ended_not_cleared不能证明死亡。固定四项精确指标维持严格覆盖，不用旧聚合摘要替代。若只能定位一两个有价值片段则少出卡，不以填满为目标。每次业务修改先在轮次计划写问题、假设、改动与验收，再实现、运行、复评、写下一轮计划。

## Validation Strategy

详见evaluation.md。以真实对局验证趣味与实际应用，以合成配对验证“看似相同、结论不同”的边界。代码、模型、人工评审分工，不以文本完全一致作为唯一答案。

核心配对：没上手/上手没能量/能用未用；有斩杀/受规则限制；同名副本；自动打出；过量/实际扣血；叠甲/抗伤；十次SL/重连；完整/有缺口。

对照纯纪录、直接总结、带工具Harness，记录输入覆盖和预算；按整局划分开发/测试，不把同一局SL尝试拆进两组。趣味与本局特色、误归因、失误误判独立报告。

## Risks / Trade-offs

- 游戏字段和Hook语义变化：按字段报告支持，不以Hook安装成功冒充完整数据。
- 永久卡到战斗副本的身份关系不足：限制实例级结论，优先完成可核实的牌型/战斗故事。
- 纯时间相邻不一定能计算卡牌贡献：故事可先发现，精确归因另查来源。
- 负面事实需要完整覆盖：缺口时允许保守表述，评测同时观察漏选。
- 模型会偏爱戏剧性：误判与趣味分离，不用责怪玩家制造故事。
- 多轮查询增加耗时与费用：后台生成、预算和缓存，测量后调整。
- 反事实验证范围有限：未支持机制明确拒绝，不伪装全游戏模拟器。

## Definition of Done

1. 本局记录能支撑已声明支持的故事情境，并标注剩余缺口。
2. 固定指标、对象身份、有效尝试、SL、零次证明等硬样本全部通过。
3. 模型能经工具取得证据并生成少量有反差的短卡；旧数据/无Key/失败可降级。
4. UI无逐回合过程和回放入口，篇幅及缓存/清空行为通过实际renderer验证。
5. 真实对局有分项评测与人工反馈，局部反事实单独验收。
6. 记录实际命令、游戏/模型版本、样本范围与限制；不能用本计划的文档校验替代业务验收。
