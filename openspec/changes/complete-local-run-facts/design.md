## Context

见 `proposal.md`。当前实现以 `RunState` 对象引用变化作为换局信号，并在状态消失时立即结束对局；读档会替换对象，因此一局被拆成多条。结束结果又以 HP 为兜底，导致 v0.107.1 抵达建筑师后的剧情死亡被记为失败。

当前 Mod 只直接 Hook 奖励界面。`card.played` 没有生产点，伤害来自每 200ms 的活敌生命总差，奖励刷新会重复发送 opened，选择依靠牌组差分。Electron 只存最终快照和计数，没有原始事实记录器。已接入的 `SaveManager.IncrementNumReloads` 能确认读档，但现有 `save-loads.json` 尚未与运行中的对局上下文关联。

## Goals / Non-Goals

**Goals:**

- 对每类数据明确权威 Hook、身份、覆盖范围和未知状态。
- 一局跨读档保持一个身份，同一遭遇跨重打保持一个战斗身份。
- 读档后从有效数据中移除该战斗前一次尝试，只统计最新尝试。
- 本地事实成为个人数据与未来复盘的唯一输入。
- 首批实现覆盖 `sts2-data-instrumentation-plan.md` 的 P0-A、P0-B 选择闭环和战斗闭环。

**Non-Goals:**

- 不保留读档前战斗尝试的出牌与结算历史；只保留累计读档次数。
- 不用轮询近似值冒充精确战斗事实。
- 不上传事实文件，不实现排行榜或反作弊。

## Decisions

### 1. 三层身份，不把读档当换局

`runId` 在游戏确认新开局时生成随机 ID，并把本机恢复线索写入 Mod 的活动局映射。读档和进程重启通过已保存对局的角色、模式、进阶、seed 哈希、地图位置及游戏存档计数核对活动映射；只有游戏确认建立新局才换 ID。原始 seed 不写入事实文件。

`combatId` 由 `runId + 地图实例 + 房间节点 + 房间访问序号` 定义。读档回到同一房间沿用它；同层事件触发的另一场战斗或重复访问使用新访问序号。

内部使用 `attemptGeneration` 防止网络中已经发出的旧事件与新尝试混合。它不作为个人统计维度，也不在最终有效事实中保留旧尝试内容。确认读档时，Mod 先发送 `combat.attempt_replaced`，再从新 generation 发布事件。

### 2. 战斗以可替换分块保存

普通非战斗事实按事件 ID 追加。活动战斗写入单独的 generation 临时块；战斗正常结束后提交为该 `combatId` 的唯一有效块。读档时新建替换块，持久提交后原子切换 manifest 指针并删除旧块。这样最终读取、导出和聚合只能看到最新尝试，同时崩溃恢复不会把两次尝试拼接。

读档发生在非战斗房间时，回退到存档点之后产生的未提交决策和构筑变化也按 checkpoint 序号回滚；已经在保存点中的永久状态通过恢复快照重新校准。

### 3. 使用版本化事实信封与源端确认

Mod 为事件分配 `eventId = sourceSessionId:sourceSeq`，源序号严格递增；重发沿用 ID。信封包含 `runId`、可选 `combatId/decisionId/actionId`、generation、发生时间、上下文快照和质量字段。

Electron 在协议校验后、业务聚合前写入 `userData/facts/v1/runs/<runId>/`。持久提交后才确认连续源序号。Mod 短时内存队列负责重连补发；无法补发时记录缺口。完整覆盖“桌面端和 Bridge 同时运行”的时间段；桌面端未运行期间标记未观察，不伪造完整。

### 4. 权威动作 Hook 与快照分工

实施前使用本机 v0.107.1 `sts2.dll` 核对并登记每个 Harmony 目标的完整签名、异步完成点、取消路径和调用次数。Hook 族按以下边界接入：

- 游戏建立新局、恢复已保存局、结束和 Architect 结局：对局身份与结果。
- 房间进入/离开、地图合法入口确认：房间和路线。
- 奖励候选刷新与明确选择/跳过完成：一个 decision，多版候选，一个结果。
- 商店成交/删牌完成、火堆动作完成、事件选项执行完成：候选、动作和实际结果。
- 永久牌组、遗物、药水实际变更：构筑时间线。
- 战斗建立/结束、阶段和回合边界、实体生成/退出。
- 卡牌实际执行、资源支付、伤害结算、格挡、治疗、资源、牌区移动、药水与 power 变化。

轮询快照只用于上下文、恢复和守恒核对。没有权威 Hook 的事件族标记 unavailable，不从净变化生成“精确”事件。

### 5. 通关是产品语义，不是 HP 大于零

对局结束记录 `cleared`、结束原因和所依据的游戏结束路径。v0.107.1 中击败第三幕 Boss 并进入 Architect 结局为 `cleared=true`；此前确认死亡、主动结束或不可恢复退出为 `cleared=false`。临时拿不到状态、Bridge 断开、应用退出和读档都只结束观察片段，不结束对局。

实际 Boss 历史来自 `combat.started/ended` 的真实遭遇，不再用地图上的 `nextBoss` 冒充已打 Boss。

### 6. 个人数据改为 fact-backed v2

新增由有效事实生成的摘要索引；最近列表只收已确认结束的 run，一局一行，标签固定为“通关/未通关”。活动局保持草稿，不显示“中断”。所有计数按事件族 coverage 筛选；缺失出牌 Hook 时显示未知，不显示 0。

现有 `review-history.v1.json` 保留为 legacy 备份，不自动混入 v2，避免已有读档碎片继续污染页面。当前 UI 布局可沿用，数据源和状态文案切换到 v2。

### 7. 分批交付但不提前宣称完整

先完成身份、存储、重打替换和生命周期；再完成选择闭环；最后完成战斗闭环。只有三批都通过实机对照，个人数据才切换到 v2。开发期间 coverage 明确显示哪些族尚未支持。

## Risks / Trade-offs

- **[风险] 游戏更新改变 Hook** → 每个 Hook 上报能力与目标构建；失败时降级为 unavailable，不输出全零。
- **[风险] 读档发生在事件/奖励中，回滚边界复杂** → 使用存档 checkpoint 与恢复快照校准，无法证明的区间标记 gap。
- **[风险] 删除旧战斗尝试降低调试能力** → 这是用户确认的产品口径；仅保留读档次数和替换健康记录，不保留旧动作内容。
- **[风险] 事件量和磁盘增长** → 分战斗块、关键快照、批量追加和可配置保留；实机测量后定上限。
- **[风险] 旧个人数据消失** → v1 文件原样保留并可导出，但不把已知错误数据包装成 v2。
- **[风险] 同 seed 新局与读档混淆** → 只有新局建立 Hook 可创建 runId；seed 哈希只作恢复线索。

## Migration Plan

1. 加入新协议和 Replay 夹具，但保持旧状态协议可读。
2. 建立 facts/v1 记录器、确认和 coverage，先影子记录，不切个人数据。
3. 接入稳定 run/combat 身份与读档替换，验证十次重打仍为一局一战斗。
4. 接入选择与构筑 Hook，完成候选到结果闭环。
5. 接入战斗动作与结算 Hook，和实机逐动作对照。
6. 启用 fact-backed v2 个人数据；把 v1 重命名为 legacy 备份。
7. 回滚时停止 v2 写入并恢复旧 UI 数据源；facts 文件保留，不删除玩家数据。
