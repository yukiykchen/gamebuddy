## Context

见 `proposal.md`。确认读档已经由 `SaveManager.IncrementNumReloads` 写入 Mod 目录的 `save-loads.json`，但 `ObserveReload` 在对局身份尚未建立时直接返回，战斗外的读档也不会留下可汇总的对局事实。个人数据摘要已有 `ascension`、起止时间和终局牌组；`playtimeSeconds` 只出现在实时状态的结束事件里，没有进入事实摘要。连胜没有字段。仪表盘只取最近 50 局展示，历史文件本身保留更多已结束对局。

## Goals / Non-Goals

**Goals:**

- 每次确认读档都成为所属对局的一条事实，结束时给出包含 0 的次数。
- 用时只累加各段观察，不把两次会话之间的关机时间算进去。
- 连胜由已保存的结束结果按时间重算，修正放弃或战败后后面的连胜跟着变。
- 个人数据页能读到当前连胜、平均读档，以及每局进阶、用时、读档次数。

**Non-Goals:**

- 不改战斗尝试的替换语义，也不用读档事实代替 `combat.attempt_replaced`。
- 不从旧的 `save-loads.json` 猜测每局次数。

## Decisions

1. **读档事实与战斗替换分开计数。** 确认读档时写 `run.reloaded`，次数只数这种事实。已有的 `combat.attempt_replaced` 继续只负责丢掉旧战斗尝试。战斗中的一次读档可以同时产生两者，但平均读档不把替换事件再加一次。
2. **身份未就绪时先暂存，只在这次读档对应的继续对局上补发。** `IncrementNumReloads` 发生在已保存对局的建立过程中，postfix 可能早于对局身份。暂存这次读档，继续对局的身份一旦建立就补发。新开局不领取这笔暂存。进程内只保留尚未补发的一次，避免串到下一局。
3. **结束事实带上 `reloadCount`。** 只有新捕获的结束事实带非负整数，才能把「0 次」和「旧记录没有该字段」分开。摘要优先采用结束事实里的次数；没有该字段时，若存在 `run.reloaded` 则用其条数，否则为未知。
4. **用时按会话相加。** 一次会话从 `run.started` 或 `run.resumed` 开始，到下一次 `run.resumed` 之前的最后一条事实，或到 `run.ended`。各段秒数相加后写入 `playtimeSeconds`。没有开始或继续事实时为未知。
5. **连胜在汇总仪表盘时按结束时间从旧到新重算，并写回每局。** 通关的连胜是向前连续通关数，未通关和放弃为 0。当前连胜从最新已保存对局往回数，不受 50 局展示截断。平均读档只用最近 50 局中次数已知的对局，保留一位小数。
6. **展示放在个人数据页，不放进百分比统计条。** 页头显示当前连胜和平均读档。每局一行显示进阶、用时和读档次数；未知写「未知」。用时不足 1 分钟显示秒，否则显示分钟。终局牌组仍在展开时读取。

## Risks / Trade-offs

- [游戏仍加载旧 Mod，新对局不会带上 0 次读档] → 构建并更换 DLL 后完全退出游戏再开。更换前结束的对局保持未知。
- [会话中间长时间停留在菜单仍会计入用时] → 只排除由下一次继续对局隔开的关机间隔，不估计玩家是否在操作。
- [历史被截断后，更早的连胜无法恢复] → 当前连胜只承诺已保存对局范围内的连续通关。

## Migration Plan

1. 先补事实与摘要测试，再改个人数据展示并用现有渲染检查核对。
2. 用本机 STS2 程序集构建 Mod，备份现有 `gamebuddy_bridge.dll` 后替换。游戏正在运行时，新 DLL 要等完全退出并重新启动才生效。
3. 回滚时换回备份 DLL。已写入的 `reloadCount` 和连胜可留在本地历史中，旧版本忽略未知字段。
