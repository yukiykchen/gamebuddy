## Context

见 `proposal.md`。当前评分器把轴覆盖、少量遗物、协同和最高 12% 的 setup 稀释合并成 0–100 分；`started/mature` 只检查分数与轴存在。结果能表达“收集过哪些组件”，但不足以阻止 87 张全卡杂牌堆成熟。候选协议已有四套 `beforeScore/deltaPoints/started`，游戏内面板通过 Hitbox 事件和扩大 24 像素的矩形推断当前候选，尚无可靠的锁定语义。

## Goals / Non-Goals

**Goals:**

- 保留“先收集潜在组件、后补闸门”的正反馈，同时让稳定性成为高分和成熟阶段的必要条件。
- 将成型过程拆成结构进度、稳定性和阶段，使候选能解释“补轴”与“跨阶段”。
- 统一桌面端、WebSocket、Mod 的构筑点与阶段口径。
- 候选定位优先使用游戏自身悬停/焦点信号，并在不消费输入的前提下记录点击。
- 只在实际拿牌确认造成阶段跃迁时给出一次成型反馈，让玩家感知“这套牌刚刚接上了”。

**Non-Goals:**

- 不把楼层、生命、敌人和即时战力混进构筑进度；这些仍由综合推荐处理。
- 不在本次扩展第五流派，也不重新编写 87×4 卡牌角色矩阵。
- 不让构筑进度直接改变推荐排序。

## Decisions

### 1. 用核心闭环把 0–59 与 60–100 分开

保留现有各轴饱和、条件和协同计算，先得到 `blueprintScore`。每套流派另行声明 `coreLoop`，表示能让该流派成为主要运转来源的最小闭环：

- 自动打击：地狱狂徒闸门，加循环、兑现或打击弹药之一。
- 消耗：无惧疼痛或黑暗之拥收益闸门，加主动消耗出口或批量消耗事件之一。
- 力量：可靠力量来源，加多段攻击或兼具来源与输出的平衡组件。
- 格挡：格挡积累闸门、有效格挡来源与格挡转伤害三者齐备；只有生存能力不算格挡流爆发闭环。

闭环未齐时保留已收集组件的蓝图进度，但最高锁在 59 点。闭环齐备时直接进入 60–100 区间，60 以上由理想蓝图覆盖和闭环组件汇合稳定性共同决定：

```text
unclosedScore = min(59, blueprintScore)
blueprintRatio = blueprintScore / 100
idealCoverage = blueprintRatio²
reliableCoverage = √blueprintRatio × coreConsistency
closedScore = 60 + 25 × idealCoverage + 15 × reliableCoverage
```

其中 `coreConsistency` 为前 10 张牌内同时见到最小闭环各要求的概率。理想覆盖使用平方曲线，稳定性增益按蓝图覆盖的平方根缩放：避免只有最小闭环的紧凑牌组直接跳到 80 分以上，同时让厚度变化在低完成度牌组上仍能产生可见差异。两部分均保留原有组内饱和，确保第二份关键组件提高稳定性但不能无限叠分；只有蓝图覆盖与稳定性都趋近 1 时才能接近 100。初始 25/15 权重通过固定牌组和真实样本校准，但 60 分闭环边界不可漂移。

按当前牌组张数及各组实际张数估算前 10 张牌内同时见到闭环要求的概率；同一张牌只归属本流派的一个结构组，因此使用包含-排除或等价的无放回精确计算，避免把各组概率错误当作独立事件相乘。牌组中的中性过渡牌不直接扣“纯度分”，但会自然降低该概率；明确软反和硬毒仍从蓝图覆盖中扣除。

### 2. 阶段与 60 点启动线保持一致

输出统一 `stage: unformed | started | formed`：

- `unformed`：核心闭环尚未形成，分数范围 0–59。
- `started`：核心闭环形成且达到 60 点，但尚未满足成型条件。
- `formed`：达到 85 点、理想轴齐备且闭环稳定性达到 0.60。

不再对启动设置独立于分数的稳定性门槛，避免出现“61 点但未启动”的矛盾状态。迁移期继续派生旧 `started` 和 `mature` 布尔值，避免已有消费者立即断裂。

### 3. 用版本化基准牌组约束调参

新增稳定夹具，至少包括起始牌组、四套专注成型牌组、四套缺闸门牌组、混合牌组、87 张全卡杂牌堆及复制全卡堆。断言关注排序和阶段，不把所有精确分数写死：

- 专注构筑对应分数高于杂牌堆。
- 全卡堆没有任何 `formed`。
- 缺闸门牌组保留正进度但为 `unformed`。
- 补齐最后必要轴的候选产生阶段跃迁。

这比只测试“第二张不少于第一张 45%”更能保护产品目标。

### 4. 协议发送前后真实状态，不由 UI 推算

每条流派影响新增：

```text
beforeScore, afterScore, deltaPoints,
beforeStage, afterStage,
completedAxes
```

`deltaPoints` 继续由未取整原始差计算；UI 直接展示 `beforeScore → afterScore`，不自行做加法，避免取整差一分。协议保留旧 `started` 字段和自动打击顶层别名；Mod 对新字段做原子校验。

### 5. 候选选择采用明确优先级

面板当前候选按以下优先级解析：

1. 游戏控件明确报告的当前悬停候选；
2. 当前键盘/手柄焦点候选；
3. 最近一次未被消费的点击候选；
4. 无候选，只显示当前牌组。

不再用 `Grow(24)` 后相互重叠的矩形作为主判断；几何检测仅作为无事件时的回退，并选择鼠标点到卡牌中心距离最近者。点击监听只观察输入，不调用 `AcceptEvent`，游戏仍负责最终选牌。

### 6. 展示优先讲成型，再讲分数

面板固定显示四套当前构筑点和阶段。悬停候选时：

- 有阶段跃迁：优先显示“启动”或“成型”；
- 有新补齐轴：显示该轴的短名称；
- 其余情况显示 `当前 → 加入后（变化）`。

桌面端和游戏内统一移除 `%`，脚注明确“构筑点不是胜率”。综合推荐与流派提示方向不同时，两者继续并列展示，不自动改推荐。

### 7. 用牌组差分确认实际拿牌，再触发一次阶段反馈

候选点击只能用于预览锁定，不能作为实际拿牌事实：玩家可能用键盘/手柄选择、点击后取消，或直接跳过。Mod 在奖励打开时保存当前牌组的 `cardId + upgraded` 多重集合及候选集合；奖励关闭后的首个稳定状态与基线比较：

- 恰好有一个候选键增加一张时，发布 `card.reward.selected`，包含奖励签名、卡牌 ID 和升级状态。
- 没有候选增加视为跳过；多个候选同时增加或无法匹配时保持未知，不猜测。
- 同一奖励签名最多发布一次确认事件。

桌面端在发送 `draft_impact` 时按奖励签名缓存每张候选的前后阶段和补齐轴，收到确认事件后只接受同签名、同候选的缓存。若存在向上阶段跃迁，则：

1. 游戏内铜铁面板短暂强调对应流派；`started` 使用一次铜色推进，`formed` 使用更明确但无全屏遮罩的完成强调。
2. 桌宠显示一条本地确定性短句，例如“力量轴接上了。”或“核心循环完整了。”；短句由流派、目标阶段和补齐轴模板生成，不调用 LLM。
3. 同一张牌同时启动多套时合并为一条反馈，优先展示更高阶段，再按流派固定顺序列出，避免连续刷屏。

普通点数变化、仅补轴但未跨阶段、预览、跳过和未知选择均不触发拿牌后反馈。曾考虑直接使用最后点击卡牌，因无法覆盖键盘/手柄且可能误庆祝而放弃。

## Risks / Trade-offs

- **[风险] 闭环补齐时从 59 以下跳到 60 以上显得突兀** → 这是刻意保留的“启动”爽感；候选 UI 同时显示补齐轴和阶段跃迁解释跳分。
- **[风险] 稳定性继续过度惩罚必要过渡牌** → 中性牌不直接扣分，只通过闭环组件真实上手概率影响 15 分稳定性区间。
- **[风险] 固定前 10 张不能模拟所有抽牌与费用情形** → 它只表示早期组件汇合概率，不声称模拟战斗；后续可按流派配置窗口，不引入即时战斗状态。
- **[风险] 协议新增字段造成旧 Mod 不识别** → 保留旧字段，桌面端仅向支持新格式的当前 Mod 发布；坏消息继续原子拒绝。
- **[风险] 监听点击可能与游戏 UI 生命周期竞态** → 不消费事件，奖励关闭时立即清理；实机验收覆盖单击关闭与点击后仍打开两种行为。
- **[风险] 奖励关闭与牌组状态更新顺序不固定** → 在关闭后等待首个稳定快照并只比较候选多重集合；超时或不唯一时宁可不庆祝。
- **[风险] 多流派同时跃迁导致反馈噪声** → 每次拿牌只生成一个合并反馈，按“成型优先、固定流派顺序”选择内容。
- **[风险] 四套范围仍漏掉自伤构筑** → UI 保持“铁甲四套构筑”措辞，不宣称覆盖全部玩法；第五流派另开变更。

## Migration Plan

1. 先加入基准牌组和协议失败测试，锁定当前错误与兼容字段。
2. 实现结构/稳定性分离、三阶段和候选前后状态。
3. 扩展候选协议及桌面端展示，再更新 Mod codec、拿牌确认事件和面板交互。
4. 接入一次性阶段反馈与桌宠确定性短句，覆盖跳过、未知选择和多流派合并。
5. 运行 Node、Harness、Mod 测试，并在真实三卡奖励页验证鼠标、键盘/手柄、点击、拿牌确认和降噪。
6. 回滚时可恢复旧分数公式和面板渲染；保留新增协议字段不会影响旧消费者。
