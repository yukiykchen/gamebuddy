## Context

见 proposal.md。已检查本机进程，GameBuddy.exe 通过应用宝 YYBPackage 运行。源码 main.js 每批消息调用 showInactive，随后发送窗的 showComposerHost 无条件设置穿透并 moveTop；Windows 40ms 光标探测在发送窗内反复调用飞行层 setIgnoreMouseEvents。renderer 同时处理 pointerenter/leave、mousemove 和主进程探测。上述为可疑路径，尚未复现证实因果。

源码已经全局 disableHardwareAcceleration，并在 Wine 环境变量存在时追加 GPU 参数。不能假设再次关闭加速可修复，也不能假设运行中的安装包已包含所有未提交源码。

## Goals / Non-Goals

**Goals:** 最小化连续显示中的原生窗口变更，保存悬停详情、发送交互和透明外观；验证应用宝中的真实表现。

**Non-Goals:** 不更换渲染架构，不关闭悬停，不调整模型与弹幕排队，不盲目增加 Chromium 参数，不覆盖当前运行安装目录。

## Decisions

1. 实施前核对安装版版本和 ASAR 内相关逻辑，以本地回放区分持续滚动、新消息到达、悬停三种触发条件。测试使用本机假服务，不发送真实共享消息。
2. 将显示操作限定在不可见到可见的转换；发送窗仅在初次显示、用户展开或有证据表明层级失效时调整层级。避免消息到来就重复激活窗口链。
3. 主进程统一维护已应用的鼠标穿透状态，仅变化时调用原生 API；清理、隐藏及重建时同步状态。若复现悬停事件振荡，稳定命中目标并避免同一位置反复切换，不以删除悬停绕过。
4. 保留目前 GPU 设置作为对照基线；若窗口状态去重不能消除连续滚动闪烁，记录证据并修订设计后再考虑渲染方案，不能宣称当前候选修复已解决问题。
5. 回归记录同一窗口在多批消息中连续可见、焦点未变、鼠标模式无多余切换；应用宝安装版额外观察至少60秒持续弹幕。原生 Windows 和 Mac Electron 结果分开报告。
6. 用户截图指出0.2.12包内main.js:1094的桌宠加载回调访问已销毁对象，路径对应本机隔离验证。加载及就绪回调捕获原窗口与原WebContents，执行前检查销毁、退出及当前引用；旧窗口回调不能对替代窗口发送消息或显示它。只保护回调入口，不增加全局uncaughtException吞错。

## Risks / Trade-offs

- [去掉重复抬升可能使按钮被遮挡] → 回放新消息期间执行展开、关闭、再次展开，验证层级与点击。
- [安装版与源码不同] → 先核对实际产物，不把源码检查当作当前运行行为。
- [兼容层合成问题无法由状态去重解决] → 保留前后对照及未解决状态，不用自动化断言替代视觉验收。

## Migration Plan

先完成局部回归，再构建独立候选安装包并核对ASAR，保留旧包以便回退；不替换运行中的应用或用户数据。
