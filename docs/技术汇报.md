# GameBuddy 技术汇报

GameBuddy 是面向《杀戮尖塔 2》的只读 AI 桌面助手。本文介绍项目当前的技术架构、Agent 实现方式，以及 OpenSpec 在开发流程中的作用。

- 项目版本：`0.1.0`（原型）
- 策略数据基线：游戏 stable `v0.107.1`
- 产品边界：只提供建议，不点击、不出牌、不修改存档，也不控制鼠标

---

## 1. 项目概览

玩家在选牌、地图分叉和休息处等场景中，经常需要结合牌组、生命和后续路线快速判断。游戏会展示选项，却不会解释某个选择为什么更适合当前对局。

GameBuddy 通过游戏内 Mod 只读采集对局状态，经本机 WebSocket 发送给 Electron 桌面端。桌面端先用规则分析合法选项，需要时再让大语言模型（LLM）复核，最后在主面板和悬浮桌宠中展示建议与理由。

系统支持三种运行方式：

| 运行方式 | 数据来源 | 主要用途 |
| --- | --- | --- |
| Demo / Replay | `harness/` 中的固定回放样本 | 无需安装游戏即可体验 UI 和 Agent |
| 真机 LIVE | Windows 上的 GameBuddyBridge | 获取真实对局建议 |
| 录制回放 | 真机录制的 fixture | 离线开发和回归测试 |

当前覆盖选牌、路线、休息处、事件和小怪 / 精英 / Boss 攻略。战斗出牌顺序、自动操作和多人合作策略不在现阶段范围内。

### 1.1 核心技术亮点

GameBuddy 的难点不在于“调用一次大模型”，而在于把实时建议做成一个可控、可复现、能随游戏版本持续演进的工程系统。

1. **用稳定协议隔离高频变化的游戏内部实现。** C# Mod 负责适配 Harmony 和 Godot，Electron 与 Agent 只依赖 `gamebuddy.state.v1`。游戏升级后，主要调整 Bridge，不需要让 UI 和决策层跟着理解新的内部类名。
2. **把模型限制在代码生成的合法选项内。** 路线、卡牌、休息处和事件候选均由规则层枚举；LLM 只返回下标和理由。系统没有点击、出牌或修改游戏状态的接口，从架构上守住“只建议”的边界。
3. **真机链路可以完整替换为 Replay。** 固定回放与 Mod 使用同一协议，下游 Observation、Agent 和 UI 不需要分叉。开发者无需启动游戏、Windows 环境或 API Key，也能复现一次选牌和一次地图决策，并把它放进 CI。
4. **按实时系统处理异步竞态。** 状态与事件分流，Observation Store 维护序列号和场景窗口；Orchestrator 用签名去重、generation 丢弃过期结果，并在奖励关闭或进入战斗时清理请求，避免慢模型把上一场景的答案写进当前 UI。
5. **机制事实与策略观点分层维护。** 卡牌文本和怪物招式来自 Bridge / Spire Codex，单卡评价和遭遇打法来自带版本号的本地档案。stable 与 beta 数据分开更新，既能利用社区经验，也不会让旧攻略覆盖当前局面。
6. **用 OpenSpec 管住跨层行为。** 一个需求从协议、Agent 到桌宠可能横跨多处代码。项目先把可观察结果、非目标和验证场景写成 change，再分任务实现，使人和不同代码 Agent 可以围绕同一份规格接力。

这些设计已经落到可检查的实现上：4 类推荐任务、63 个普通遭遇机制策略、24 个精英 / Boss 社区复核档案、最多 256 条地图路径、4 种桌宠姿态，以及覆盖协议、Replay 和 Agent 的自动化验证。技术亮点不是单个模型能力，而是围绕模型建立的约束、回放和演进机制。

## 2. 技术架构

### 2.1 总体链路

```text
《杀戮尖塔 2》进程
        │  只读采集（Harmony / Godot 节点）
        ▼
GameBuddyBridge（C# Mod）
        │  WebSocket  ws://127.0.0.1:27182
        │  消息：state / event
        ▼
Electron 主进程（main.js）
        │  协议校验 → Observation Store
        ▼
Agent（agent/）
        │  规则生成合法候选 → 可选 LLM 复核
        │  输出 gamebuddy.recommendation.v1
        ▼
preload.js（contextBridge）
        ├─ 主面板（src/index.html + renderer.js）
        └─ 悬浮桌宠（src/pet.html + pet.js）
```

开发环境可以用 Replay Bridge 替换游戏和 Mod，后续链路保持不变。桌面端只依赖协议字段，不依赖游戏内部类名；游戏升级时，改动主要集中在 Mod 适配层。

### 2.2 技术栈

| 层次 | 技术 | 用途 |
| --- | --- | --- |
| 桌面端 | Electron 37、原生 HTML/CSS/JS | 主窗口和透明置顶桌宠窗口 |
| 进程通信 | Electron IPC、`preload.js` contextBridge | 隔离渲染进程与 Node / 文件系统 |
| 实时通道 | `ws`（WebSocket） | 通过本机环回地址传输状态与事件 |
| 运行时 | Node.js 20+ | Agent、Harness 和知识同步脚本 |
| 游戏 Mod | C# / .NET 9、Godot 4.5.1、Harmony | 接入游戏并只读导出状态 |
| 打包 | electron-builder、Windows NSIS x64 | 生成 Windows 安装包 |
| LLM | OpenAI 兼容 HTTP API | 支持 Responses API 和 Chat Completions |
| 知识来源 | 本地 JSON、Spire Codex HTTP API | 提供卡牌评价、遭遇策略和机制数据 |
| CI | GitHub Actions | 校验协议和 Replay，构建桌面端与 Mod |

项目没有引入前端框架。除 Electron 相关依赖外，核心运行时依赖主要是 `ws`，协议校验、决策逻辑和 UI 均保留在仓库中，便于离线运行和审查。

### 2.3 桌面端职责

- **主面板**：提供战斗、选牌和地图三个工作台；侧边栏展示角色、进度、牌组、遗物和金币。
- **悬浮桌宠**：独立透明窗口，支持置顶、拖动和托盘显隐。桌宠有 `waiting`、`watching`、`thinking`、`advising` 四种互斥姿态，优先级为“建议 > 思考 > 等待 > 旁观”。建议卡采用渐进披露：默认只显示一句具体决策，点击“展开理由”后再显示分析、风险、备选和来源，窗口高度随展开状态调整。
- **主进程**：维护 Bridge 连接和重连，写入 Observation Store，调度 Agent，并向两个窗口广播状态、建议、攻略和思考状态。

实时链路超过 5 秒没有可用新状态时，界面会提示 `STALE`。地图、奖励和事件属于停留型界面，由当前场景数据及打开 / 关闭事件管理，不会仅因为玩家停留超过 5 秒就立即清空。

### 2.4 数据契约

`gamebuddy.state.v1` 是 Mod 与桌面端之间的稳定边界，主要包含：

- `run`：幕、楼层、房间、角色、当前位置和 Boss 身份等；当前没有整局 UUID 或 seed
- `player`：生命、能量、金币、牌组、遗物和药水
- `combat`：手牌、抽牌堆 / 弃牌堆 / 消耗堆、敌人及 `NextMove` 类型；非战斗时为 `null`
- `map`：当前幕的有向无环图（DAG）、已访问节点和可达路线；路线最多保留 256 条

状态快照与事件分开发送。当前事件包括 `combat.started` / `ended`、`turn.started`、`map.opened`、`rest.opened` / `closed`、`event.opened`、`card.reward.opened` / `closed` 等。奖励和事件界面优先依赖明确的生命周期事件，减少通过 UI 状态猜测场景的情况。

Observation Store 将最新快照和近期事件整理为 `gamebuddy.observation.v1`，并附带序列号、接收时间、数据年龄和 `fresh` 标记。Agent 只消费 Observation，不直接读取游戏进程或原始 WebSocket 帧。

## 3. Agent 的设计与实现

这里的 Agent 指推荐引擎，而不是让模型直接接管整局。它先确定当前场景，再枚举合法动作、执行规则评分，最后按配置决定是否调用 LLM。

### 3.1 决策流程

一条推荐通常经过五步：

1. Orchestrator 识别当前场景。
2. 任务模块从协议数据中生成合法候选。
3. 规则层评分，并为候选生成理由。
4. 配置了 LLM 时，模型只能返回候选下标和简短说明。
5. 程序校验结果，并输出 `gamebuddy.recommendation.v1`。

合法候选始终来自当前状态：

- 路线只能指向地图上真实可达的下一节点。
- 休息处只能选择回血或升级牌组中尚未升级的牌。
- 卡牌奖励只能选择当前奖励牌或 `SKIP`。
- 事件只能选择协议中的 `event.options`。
- 只有 `exact=true` 的 Boss / 精英才能作为已确定遭遇；没有 `encounterId` 时不猜具体敌人。

未配置 API Key 时，选牌、路线、休息处和事件都使用规则结果。模型调用失败后的处理略有不同：

- 路线、休息处和事件会回退到规则结果。
- 卡牌奖励在启用模型后会等待模型完成；调用失败或返回非法下标时，不发布新的选牌建议。如果同一奖励界面已有合法建议，则保留原结果。

这一区别是为了避免选牌界面先显示一个答案，随后又被慢请求改成另一个答案。

### 3.2 场景调度与并发

Orchestrator（`agent/orchestrator.js`）按以下优先级选择任务，同一时刻只运行一个推荐任务：

```text
存在 combat              → 不运行推荐任务，小怪 / 精英 / Boss 攻略走独立通道
存在卡牌奖励             → card_reward
存在事件选项             → event_choice
刚打开休息处且选择未完成 → rest_site
休息处已选完且下一步有分叉 → map_route
地图下一步有多个选择     → map_route
其他情况                 → 空闲或清理过期建议
```

为避免重复请求和异步结果串场，运行时还做了几层保护：

- 每个任务都有场景签名；输入没有变化时不重复计算。
- generation 号用于丢弃晚到的旧结果。
- 同一选牌请求进行期间，后续同场景快照复用这次请求。
- 奖励关闭、进入战斗或地图不再分叉时，结束思考并清理对应建议。

仓库中的 `agent/agents/*` 和 `router.js` 是较早的决策录制链路，输出 `runmate.decision.v1`。主面板和桌宠目前使用 Orchestrator 与 `agent/tasks/*`。

### 3.3 卡牌奖励（`card_reward`）

任务由 `card.reward.opened` 或状态中的奖励字段触发，奖励关闭后立即停止。

规则层会为每张候选牌给出 0–100 分，并生成优点、风险和适用场景。评分主要考虑：

- 攻击、格挡、抽牌、能量、成长、控制、群体和消耗等机制
- 当前牌组的攻击 / 防御密度、厚度和机制协同
- 未来约三层内的精英，以及是否接近 Boss
- 已确定与可能遭遇的机制标签
- 带版本号的本地单卡评价
- Spire Codex pick-coach 中相似胜局的采用率和 offer-conditioned 拿取分

当牌组已经较厚、候选牌又没有明显提升时，`SKIP` 可以成为最高分选项。

LLM 复核会收到完整牌组与升级状态、遗物和药水效果、生命与金币、地图、遭遇信息，以及规则层整理过的候选分析。模型只能返回候选下标。最终建议卡会展示推荐牌或跳过、当前局面的理由、主要收益、风险、来源和置信度。

### 3.4 地图路线（`map_route`）

路线任务只在当前位置出现分叉时触发。单路前进不调用模型，也不额外打扰玩家。

地图按 DAG 处理。如果 Bridge 没有提供 `routes`，桌面端会从当前位置沿 `children` 枚举通往 Boss 的路径，最多 256 条。每条路径分别计算收益和风险，主要因素包括：

- 精英：遗物收益和当前生命风险
- 火堆：回血需求和可升级牌数量
- 商店：金币、牌组厚度及删牌价值
- 宝箱、远古和问号节点的基础收益
- 精英后衔接火堆等节点组合

同层出现多个同类型节点时，建议使用 `targetId`、行列和方向标签区分。若最高分路线没有可验证的差异，结果会明确标为平局，而不是强行给出唯一答案。

### 3.5 休息处（`rest_site`）

休息处只有两类合法动作：回血，或升级牌组中一张尚未升级的牌。

策略封装在 `agent/skills/rest-site-strategy/`。它逐张比较升级前后的文本，识别降费、抽牌 / 能量、保留 / 消耗变化、倍率成长、多目标和控制等变化，再结合使用频率、牌组协同、遗物、当前幕、生命比例和近期强敌评分。

低生命或即将面对高压战斗时，回血权重会上升；生命健康且存在高价值升级时，更倾向锻造。模型复核时会收到相同的策略摘要、完整牌组、遗物、药水、地图和最多 10 个真实升级候选。策略权重以 stable `v0.107.1` 为基线，版本更新后需要重新核对卡牌文本。

### 3.6 事件选择（`event_choice`）

事件候选完全来自 `event.options`。Agent 将运行时动态效果与 stable `v0.107.1` 的 66 条 Spire Codex 事件、56 棵页面决策树匹配，逐项提取生命、最大生命、金币、删牌、升级、遗物、药水、负面牌、战斗和随机性，并结合玩家资源输出收益、代价、风险、规则分数与置信度。

锁定、金币不足或明确致死的选项会在模型调用前被排除。配置 LLM 后，模型只在规则允许的真实索引中结合牌组、遗物和药水复核；没有模型或模型失败时使用可解释的规则首选。若全部选项效果未知，系统不再默认选择第一个按钮，而是停止思考并提示资料不完整。

### 3.7 小怪 / 精英 / Boss 攻略

任何战斗在 `combat` 非空时，主进程都会通过独立的 `gamebuddy.encounter-guide.v1` 通道发送攻略。攻略不会占用选牌、路线或休息处的 recommendation 槽，并且每场只自动弹出一次；玩家关闭后可在当前战斗通过桌宠上的攻略按钮重新打开。

内容分为两层：

- **机制数据**：来自 Spire Codex，包括血量、能力、招式和行动模式。
- **策略数据**：63 个普通遭遇按实际敌人组合使用 Spire Codex 机制推导；`encounter-strategies.json` 覆盖当前版本 12 个 Boss 和 12 个精英，记录危险窗口、牌组检查、目标优先级、常见失误、来源和置信度。

每场遭遇按幕、楼层和坐标去重，只自动弹出一次。关闭操作只隐藏面板并保留当前攻略缓存，不会因回合或生命变化再次自动弹出；战斗结束时缓存与重开按钮一并清理。无法确认敌人 ID 时不展示推测攻略。同一份策略数据也会进入选牌上下文，让选牌判断能够参考已知 Boss 和可能精英的机制。

### 3.8 知识与 LLM 接入

本地知识包括：

- `card-evaluations.json`：全卡 rank、中文摘要、适用 / 避用条件、版本和来源
- `encounter-strategies.json`：精英与 Boss 策略及审核状态
- `events.json` + `event-rules.js`：66 条事件决策树、运行时效果解析和安全门禁
- `rest-site-strategy`：休息处权重、生命阈值和社区证据

卡牌评价可通过 `npm run knowledge:cards` 按 stable / beta 渠道更新。

运行时默认从 `https://spire-codex.com/api` 补充卡牌描述、怪物招式和 pick-coach 数据。接口超时或失败时，Agent 仍可使用 Bridge 数据和本地知识。

LLM 客户端位于 `agent/llm/openai.js`，支持通过环境变量配置 Base URL、模型、API Key、Responses / Chat 协议、reasoning effort 和 thinking 开关。各任务使用独立提示词，并要求返回 JSON `{index, reason}`。默认请求超时为 120 秒，请求开始和结束会同步驱动桌宠的 `thinking` 状态。

### 3.9 Agent 的开发方式

Agent 按“协议 → 观察对象 → 规则 → 模型 → UI”的顺序迭代：

1. **记录局面。** 真机通过 `harness:record` 保存合法的 state / event；没有游戏时使用现有 Replay。
2. **先写纯任务函数。** `recommendCardReward`、`recommendRoute` 和 `recommendRest` 只接收 observation / state 并返回 recommendation，不直接调用 Electron 或操作游戏。
3. **先验证规则模式。** 打分、`SKIP`、平局和分叉标签都使用 Node 脚本与回放样本验证。
4. **再接入模型复核。** 提示词只包含当前事实和规则候选，任务模块拒绝候选范围外的下标。
5. **最后接入 Orchestrator 和 UI。** 场景切换、思考动画、建议展示和请求取消属于产品行为，需要先写清规格。
6. **知识与代码分开维护。** 随游戏版本变化的卡牌和遭遇资料放在 JSON / Skill 中，不把易变结论散落在条件分支里。

常用验证入口包括 `npm run test:syntax`、`npm run test:agent`、`npm run harness:validate-all`、`npm run harness:validate-agent` 和 Replay Demo。Replay 通过只能证明桌面端链路可回归，不能替代 Windows 真机上的 Mod 验收。

## 4. 用 OpenSpec 协同开发

在 GameBuddy 中，OpenSpec 不只是需求文档生成器，而是一次变更的协作契约。产品、协议、Agent、UI 和测试可能由不同的人或代码 Agent 完成；只要大家读取同一个 change，就能知道为什么改、最终行为是什么、技术上怎么做，以及还剩哪些任务。

### 4.1 它解决了什么协作问题

GameBuddy 的功能通常跨越多层。例如“奖励关闭后停止思考”会同时影响事件协议、Orchestrator、LLM 请求状态和桌宠 UI。如果只在某个文件里改代码，其他协作者很难判断：

- 这是临时实现，还是已经确认的产品规则？
- 哪些行为必须保持兼容？
- 模型失败时应该回退、保留旧结果，还是不显示建议？
- 哪个 Replay 场景可以证明功能完成？

OpenSpec 将这些问题前置。仓库规定，修改可观察行为前先运行 `openspec list`；没有合适的 active change 时先提案。`openspec/changes/<name>/tasks.md` 出现之前，不修改业务代码。

需要走该流程的内容包括主面板和桌宠 UI、状态 / 事件 / recommendation 协议、Agent 的候选与回退、Mod 采集结果，以及 Harness / Replay 语义。错别字、格式化和纯注释可以直接修改。

### 4.2 四类产物如何分工

每个 change 都是一份可提交、可评审、可接力的文件集合：

| 产物 | 回答的问题 | 协作价值 |
| --- | --- | --- |
| `proposal.md` | 为什么做、做什么、不做什么 | 产品和技术先确认范围，防止需求顺手扩张 |
| `specs/<能力>/spec.md` | 用户最终能观察到什么 | 用 SHALL 与 WHEN / THEN 场景作为开发和验收的共同标准 |
| `design.md` | 跨模块如何实现、有哪些取舍 | 让后续实现者不必从聊天记录中还原技术决策 |
| `tasks.md` | 具体改哪些部分、怎么验证 | 支持拆分任务、更新进度，并为交接保留明确入口 |

仓库级约束写在 `openspec/config.yaml`：计划使用中文，OpenSpec 标题和 SHALL / MUST 保留英文；Non-goals 默认排除代打；每项行为变化都要带现有 npm 命令或 Replay 验证。

主规格和变更记录分开保存：

- `openspec/specs/`：当前已经生效的能力规格
- `openspec/changes/<name>/`：正在讨论或实现的增量
- `openspec/changes/archive/`：完成后的历史决策

这种增量方式适合现有项目：团队只描述本次行为变化，不必先为整座代码库补齐历史规格。

### 4.3 人与代码 Agent 如何接力

一次完整协作可以拆成五个责任阶段：

1. **需求提出者定义目标。** 说明用户痛点、产品边界和验收结果，不要求一开始就给出代码方案。
2. **提案 Agent 调研并写 change。** 它可以阅读现有协议、实现和测试，但提案阶段只创建 OpenSpec 文件，不碰业务代码。
3. **评审者检查四件事。** 行为是否可观察、Non-goals 是否清楚、设计是否覆盖跨层影响、任务是否包含可执行验证。
4. **实现者按 `tasks.md` 开发。** 每完成一项就勾选，并运行该项对应的最小测试。新的会话或另一位开发者可以直接从未完成任务继续。
5. **验收者按 Scenario 验证并归档。** 代码评审不只看 diff，还要逐条对照 SHALL；通过后将 delta spec 合入主规格。

协作时遵守三个原则：

- change 是当前变更的事实来源，聊天记录只用于讨论。
- 一项任务只在实现和验证都完成后勾选，不能用“后续再补”代替 SHALL。
- 实现中发现需求或设计不成立时，先更新 change，再继续编码；不能为了让测试通过而静默缩小范围。

这使 OpenSpec 也能充当跨会话上下文。无论下一位协作者使用 Cursor、Claude Code 还是 Codex，都可以从 proposal、spec、design 和 tasks 恢复完整意图，不依赖上一段对话仍然存在。

### 4.4 实际怎么操作

先在终端查看当前变更：

```bash
openspec list
```

其余命令在 Cursor 对话框中调用，不是在终端中执行：

| 阶段 | Cursor 命令 | 产出或动作 |
| --- | --- | --- |
| 探索需求 | `/opsx-explore` | 调研与讨论，不写业务代码 |
| 创建提案 | `/opsx-propose <需求或 change-name>` | 一次生成 proposal、spec、design 和 tasks，然后停下等待评审 |
| 修订计划 | `/opsx-update <change-name>` | 同步修订已有计划文件，不改代码 |
| 开始实现 | `/opsx-apply <change-name>` | 读取全部计划文件，按任务实现、验证并勾选 |
| 同步规格 | `/opsx-sync <change-name>` | 需要时先将 delta spec 合入主规格 |
| 完成归档 | `/opsx-archive <change-name>` | 检查任务与规格，更新主规格并归档 |

`propose` 和 `apply` 是两个明确的阶段。即使最初的需求写着“帮我设计并实现”，提案完成后也会先停下，让人确认范围；确认后再单独执行 `apply`。这道门禁避免 Agent 在需求仍有歧义时直接修改跨层代码。

不同工具的入口名称不同，但读取的是同一套 change：

| 工具 | 提案 | 实现 |
| --- | --- | --- |
| Cursor | `/opsx-propose` | `/opsx-apply` |
| Claude Code | `/opsx:propose` | `/opsx:apply` |
| Codex | `$openspec-propose` | `$openspec-apply-change` |

标准协作流如下：

```text
需求提出者描述目标
    → openspec list，确认是否复用现有 change
    → /opsx-propose，生成四类计划产物
    → 产品、开发、测试共同评审
    → /opsx-apply，按 tasks.md 实现和验证
    → 对照 SHALL Scenario 做 Replay / Demo 验收
    → /opsx-archive，主规格更新，决策进入历史
```

### 4.5 项目中的协作实例

**桌宠四态：`add-pet-pose-states`**

这个 change 已经归档。主规格现在明确规定四种姿态、互斥关系和优先级，因此后续功能不能顺手引入第五种姿态。它展示了主规格的长期价值：一次评审过的产品边界，会自动成为下一次变更的输入约束。

## 5. 质量保障与发布

| 验证方式 | 覆盖内容 |
| --- | --- |
| `npm run test:syntax` | 主进程、渲染端、Agent 和 Harness 的 Node 语法 |
| `npm run test:agent` | 旧 Router 决策链路的 Node 单测 |
| `npm run harness:validate-agent` | 当前任务 Agent 的推荐与并发场景 |
| `npm run harness:validate-all` | 协议、fixture、录制文件和 Mod 文件形状 |
| `npm run harness:smoke` | Replay WebSocket 握手与首包 |
| `npm run demo` | 无游戏、无 API Key 的完整桌面端链路 |

GitHub Actions 分为三条：

- Pull Request 和主干推送在 Ubuntu 上运行 Harness 校验及 Replay 冒烟测试。
- Windows 托管 Runner 构建 NSIS 安装包。
- 安装了正版游戏的 self-hosted Windows Runner 构建 Mod。

公开 Runner 无法取得游戏私有程序集 `sts2.dll`，因此不能证明 Mod 已适配当前游戏构建。真机仍需按照 `docs/windows-validation.md` 检查 Mod 加载、协议快照、战斗、奖励、地图、休息处、攻略和断线重连。

## 6. 当前状态与下一步

目前已经完成以下闭环：

- 只读采集、协议传输和 Observation Store
- 规则 Agent 与可选 LLM 复核
- 选牌、分叉路线、休息处和事件建议
- 小怪 / 精英 / Boss 攻略
- 主面板、悬浮桌宠和 Replay 开发链路
- OpenSpec 对可观察变更的约束

仍需注意以下限制：

- 战斗内出牌顺序尚未实现，当前缺少完整的合法行动枚举、能量和随机性模型。
- Mod 已完成编码，但尚未记录一轮 Windows stable `v0.107.1` 的完整真机验收结果。
- 游戏仍处于 Early Access，卡牌知识和 Harmony Hook 需要随版本复核。
- 协议没有稳定的 run ID，跨进程识别同一局只能使用地图起点等启发式规则。
- 事件规则已覆盖常见资源与风险，但未识别的特殊效果仍会明确降级，不能等同于逐事件人工攻略。
- 所有建议均为辅助信息，不保证通关或避免战损。

下一阶段优先完成三项工作：记录一轮 Windows 真机验收；用真实选牌结果回测规则权重；为游戏版本变化建立知识 diff。战斗出牌 Agent 应在合法行动能够被完整枚举和验证后再立项。

## 7. 总结

GameBuddy 的技术价值不只是“能给建议”，而是把游戏接入、AI 决策和团队协作都做成了可约束、可回放、可验证的工程闭环：本机协议隔离游戏变化，规则候选限制模型权限，Replay Harness 复现真实场景，OpenSpec 让人和代码 Agent 通过同一份 change 接力开发。最终目标是在“只建议，不代打”的边界内，持续交付可信、可解释的实时建议。
