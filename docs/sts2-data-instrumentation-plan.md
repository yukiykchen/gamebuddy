# GameBuddy《杀戮尖塔 2》前置数据埋点方案

> 编写日期：2026-10-17（Asia/Shanghai）  
> 代码审计基线：`53d9bf5`  
> 状态：供评审的采集设计，尚未实施。本文中的新增事件名、字段与模块名均为建议。  
> 目标：功能可以以后开发，但从现在开始留下未来分析所需、事后无法补回的事实。

## 1. 本次要做什么

本次只规划《杀戮尖塔 2》的游戏行为与结果埋点，为日后的个人数据、单局复盘、流派分析和战斗评分提前积累数据。

本次不实现这些功能的页面、流派评分公式、复盘文案、排行榜或跨玩家分析平台。原始数据采集不应依赖这些功能是否开发、是否打开，也不应依赖 LLM 请求是否成功。

采集应能回答一条完整的问题链：

**玩家当时处于什么状态 → 实际有哪些选择 → 做了什么 → 哪些状态发生变化 → 后续战斗结果怎样。**

### 1.1 与现有文档的关系

- [复盘数据简要需求](review-systems-data-brief.md)：描述未来四套功能需要什么。
- [产品埋点与度量设计](telemetry-design.md)：侧重产品激活、建议曝光、功能使用和远端产品分析。
- **本文**：基于当前代码，明确游戏事实应该在哪里采集、留下哪些字段、怎样保证后续可用。
- [数据协议](data-contract.md)：描述当前协议；本文新增内容尚未进入该协议。

### 1.2 核心建议

1. 先建立可靠的事件身份、关联、落盘和缺失标记。
2. 立即保存现有 Bridge 已能取得的候选、地图、库存和关键状态。
3. 补齐奖励、路线、商店、火堆、事件的实际选择结果。
4. 接入实际出牌与效果结算，不能只依赖每 200 毫秒的状态轮询。
5. 保留事实和版本，分数、风格标签、流派启动楼层以后计算。
6. 采集覆盖所有可识别角色；不能因为当前流派算法只支持铁甲就只采铁甲。

默认延续现有文档的范围：完整事实记录保存在玩家本机。若团队需要集中分析，需要另外定义经授权的导出或上传数据集；仅在本地存储并不等于团队已获得这些数据。

## 2. 当前代码实际做到了什么

以下结论来自上述代码基线的静态审计，不代表已经完成目标游戏构建的实机验证。

| 环节 | 代码位置 | 已有能力 | 对提前积累数据的缺口 |
| --- | --- | --- | --- |
| 定时采集 | `GameBuddyCollectorNode.OnProcessFrame` | 约每 200 ms 调用一次采集 | 间隔内的动作可能完全不可见，不能作为逐动作日志 |
| 状态快照 | `GameBuddyExporter.BuildSnapshot` | 角色、楼层、永久牌组、物品、资源、战斗牌堆、敌人、地图、事件、商店 | 大部分只是当前状态；缺少完整实体身份、状态效果、部分角色资源与环境版本 |
| 对局生命周期 | `EnsureRunLifecycle / BuildRunId / EndActiveRun` | 开局、结束、结果推断 | 有 seed 时 ID 只由角色与 seed 决定；重打可能撞 ID；未确认结果时默认放弃 |
| 战斗与回合 | `PublishTransitions` | 战斗开始、结束、回合开始 | 没有独立战斗 ID；没有回合结束；离开战斗时用生命大于 0 推断胜利 |
| 出牌 | `harness/protocol.js`、`review/service.js` | 协议接受 `card.played`，统计代码消费该事件 | 当前 Mod 源码没有对应发送点 |
| 伤害 | `TrackTurnDamage`、`review/service.js::updateDamage` | 通过敌人生命差估计伤害 | 不是实际结算；不能准确归因，多次伤害、治疗、死亡移除可能影响结果 |
| 奖励候选 | `CardRewardPatches`、`PublishCardRewardIfReady` | 界面打开、刷新、关闭与候选采集 | 来源和可跳过状态写死；按卡牌 ID 去重候选；候选签名不是一次奖励的身份 |
| 奖励结果 | `GameBuddyRewardSelectionTracker.Observe` | 关闭后观察稳定牌组增量，推断拿取 | 无明确跳过事件；识别失败返回空；未闭合结果没有可靠记录 |
| 商店 | `BuildShopSnapshot / PublishShopLifecycle` | 库存、价格、金币、打开/更新/关闭 | 无单笔成交；售出项被过滤后商品索引可能变化；关闭没有消费明细 |
| 火堆 | `InferRestClosed`、`harness/rest-lifecycle.js` | 根据生命、已升级牌集合变化推断动作 | 无完整动作候选；同名牌再次升级可能漏判；两侧推断需避免重复计数 |
| 事件/远古 | `BuildEventSnapshot / PublishEventLifecycle` | 页面与选项信息，打开/关闭事件 | 无选中选项及实际效果记录；打开事件仅发送可选项，锁定项需额外保留 |
| 地图 | `BuildMapSnapshot` | 节点、连接、已走路线和截断标记 | 没有一次决策的实际可选节点集合与确认选择事件 |
| 传输 | `GameBuddyWebSocketServer` | 广播事件、缓存最后一份状态 | 无事件持久队列、确认、历史补发和源端序号 |
| 接收缓存 | `harness/observation-store.js` | 校验、当前状态、默认最近 100 条事件 | 内存会淘汰；事件序号由状态计数和队列长度拼出，不能检测源端漏采 |
| 本地复盘 | `review/service.js` | 最终状态、累计次数、最近 100 局 | 没有完整事实时间线；覆盖最终状态会失去中间构筑 |
| 调试录制 | `harness/record-bridge.js` | 状态与事件录制 | 先留内存、结束写文件；按内容去重可能丢弃合法的重复动作 |
| 建议日志 | `agent/recorder.js`、`main.js::startAgentRun` | 建议结果及接受标记 | 不是游戏事实；Agent 局 ID 没有使用现有 `run.runId`，关联口径不同 |

### 2.1 需要特别修正的现有统计接口

`review/service.js::applyEvent` 等待 `card.reward.closed.data.outcome` 才能累计明确跳过或未知，但 Mod 当前关闭事件没有这些字段。因此既可能没有跳过统计，也可能没有相应未知计数。

同一位置等待 `shop.closed.data.goldSpent`，而当前 Mod 的关闭事件没有该字段。不能据现有消费数值判断玩家没有花钱。

`main.js` 的 `accept-decision` 只表明界面收到一次接受动作，不能证明游戏内实际执行了推荐。实际选择必须由游戏事实事件确认。

## 3. 未来问题与必须提前留下的证据

| 未来要判断的问题 | 现在必须收集 | 仅留最终结果为什么不够 |
| --- | --- | --- |
| 玩家常用攻击牌还是其他牌？ | 每次实际出牌的类型、主动/自动、次数和完整度 | 战后牌组无法还原出牌频率 |
| 玩家是否偏好跳过奖励？ | 每次候选、可跳过状态、明确结果 | 没拿牌也可能是取消、断线或识别失败 |
| 玩家会主动挑战精英吗？ | 决策时实际可达路线及最终选择 | 精英次数无法区分主动选择和被迫经过 |
| 玩家会怎样花钱？ | 库存、可负担性、逐笔交易、进出店资源 | 最终金币无法解释中间买卖与事件支出 |
| 火堆为什么回血或升级？ | 可选动作、生命、构筑、已知后续路线、实际动作 | 行为本身不能证明动机，也不能证明有其他选择 |
| 构筑何时补齐关键组件？ | 初始构筑、每次永久变化、遗物变化与顺序 | 最终卡组无法定位变化时点 |
| 缺的组件是没见过，还是没选择？ | 所有曾出现的候选及实际选择 | 只记拿到的牌会产生选择偏差 |
| 流派机制有没有实际运转？ | 消耗、抽牌、格挡、状态效果及来源关联 | 总次数不能证明它们由同一机制触发 |
| 构筑变化之后战斗怎样？ | 变化前后构筑、每场遭遇、实际战斗过程和结果 | 胜负无法描述变化与表现的时间关系 |
| 战斗分未来能否重新计算？ | 精确战斗事实、环境、版本和完整度 | 旧分数和聚合桶无法支持任意新公式 |

这些数据能支持描述、关联和部分受限推断，不能自动证明玩家动机、选择优劣或某项建议的因果效果。

## 4. 数据模型与公共约定

### 4.1 三类数据分开

| 类型 | 内容 | 处理方式 |
| --- | --- | --- |
| 事实事件 | 选择完成、出牌、交易、伤害结算等 | 追加保存，按事件 ID 去重；不因算法变化改写 |
| 状态快照 | 某个时点的构筑、资源和战斗局面 | 用于上下文、恢复与核对；引用对应源序号 |
| 派生结果 | 最高单回合伤害、流派分、风格指标、战斗分 | 以后重算；保存输入范围、算法及知识版本 |

状态差得到的“疑似拿牌”“疑似回血”应标注推断来源，不与直接动作事件混为同一可信级别。未来得到更准确证据时，通过追加关联或更正记录处理，不覆盖原始观察。

### 4.2 身份定义

| 字段 | 含义与要求 |
| --- | --- |
| `runId` | 一次真实对局尝试；读档恢复应沿用，新开相同 seed 应新建；优先使用经验证的游戏身份，否则使用持久化的局内映射 |
| `segmentId` | 连续观察片段；中途接入、无法确认衔接或读档回退时新建，并记录关联依据 |
| `combatId` | 一次实际战斗；不只用楼层，需区分同层多场和重试 |
| `decisionId` | 一次实际选择机会；奖励、地图、商店或事件页面等使用独立实例身份 |
| `actionId` | 一次执行动作；可以产生多条效果事件 |
| `parentActionId` | 触发当前动作的上级动作；未知时为空并注明原因 |
| `entityInstanceId` | 同一局内的卡牌、怪物等实例；与卡牌/怪物类型 ID 分开 |
| `playerSlot` | 局内玩家槽位，不使用账号或设备身份 |

seed 哈希只能是可选的局匹配线索，不是一次尝试的唯一 ID。无法可靠关联读档时，应标注未解析关联，不能按同 seed 强行合并，也不能把重新观察到的中途状态称作开局。

同一张永久牌进入战斗后的实例如可映射，保存 `originDeckCardInstanceId`。临时生成牌保存生成来源，不能写入永久构筑变化。

### 4.3 事件信封

以下为建议结构示例，值仅用于演示：

```json
{
  "schema": "gamebuddy.fact-event.v1",
  "eventVersion": 1,
  "eventId": "source-session-demo:1042",
  "eventType": "card.played",
  "runId": "run-demo",
  "segmentId": "segment-demo",
  "combatId": "combat-demo",
  "decisionId": null,
  "actionId": "action-88",
  "parentActionId": null,
  "sourceSessionId": "source-session-demo",
  "sourceSeq": 1042,
  "occurredAt": 1792195200000,
  "sourceElapsedMs": 43120,
  "receivedAt": 1792195200018,
  "act": 1,
  "totalFloor": 7,
  "nodeId": "act-1:6,2",
  "round": 2,
  "phase": "player",
  "playerSlot": 0,
  "contextSnapshotId": "snapshot-1041",
  "quality": {
    "observationMethod": "direct_hook",
    "unknownFields": ["parentActionId"],
    "unknownReasons": { "parentActionId": "not_observed" }
  },
  "payload": {
    "cardId": "STRIKE_IRONCLAD",
    "cardInstanceId": "combat-card-12",
    "originDeckCardInstanceId": "deck-card-3",
    "cardType": "Attack",
    "upgraded": false,
    "playMode": "manual",
    "targetIds": ["enemy-2"],
    "resourcesSpent": [{ "resourceId": "energy", "amount": 1 }]
  }
}
```

约定：

- `sourceSeq` 由生产者在事件产生时分配，在同一 `sourceSessionId` 内严格递增，不能由桌面端队列长度推算。
- 重发沿用原 `eventId`；同内容的第二次合法动作必须有新 ID。
- 时间戳用于展示与延迟分析；同一来源排序以序号为准。不同来源的序号不可直接比较。
- `null` 不表示 0，也不自动表示不适用；用原因区分 `not_applicable / unsupported / not_observed / gap / invalid`。
- 地图节点身份包含幕或地图实例，不能只用行列坐标。
- 非战斗事件的 `combatId` 为空；没有因果来源的动作与来源未知要区分。
- 快照必须能定位到动作前或动作后。`contextSnapshotId` 若只引用最近一次轮询，要记录快照年龄和相对动作位置，不能冒充精确前置状态。

### 4.4 对局元数据

重复不变的信息保存在对局/环境记录中，事件通过 ID 引用：

| 类别 | 字段 |
| --- | --- |
| 游戏 | 游戏构建版本、规则/内容版本或可核对的程序集摘要 |
| 采集 | Bridge 版本、App 版本、协议版本、采集能力清单 |
| 环境 | 实机或回放、游戏模式、进阶、人数、本地玩家槽位、角色、影响玩法的 Mod ID 与版本 |
| 观察范围 | 是否从真正开局开始、首次观察楼层、观察结束原因、关联是否明确 |
| 知识快照 | 卡牌/遗物/状态目录版本或内容摘要、运行时字段来源 |

未知的模式、Mod 状态或能力不能默认填“标准环境”。目录摘要用于定位另存的目录内容；只存哈希、不保留对应内容，不能支持以后解释旧版本机制。

### 4.5 关键快照

建议在以下时点保存，避免无差别持久化每帧状态：

1. 真正开局或首次接入；两者明确区分。
2. 决策机会首次出现、候选实质刷新，以及选择完成后。
3. 永久牌组、遗物、药水或角色永久资源发生变化后。
4. 进出房间、战斗开始与结束。
5. 回合开始与结束。
6. 断线恢复、源重启、疑似读档回退后的校准点。

快照按用途包含永久构筑、资源、可见路线或候选；战斗快照包含手牌、牌堆、敌我状态和意图。逐动作状态按需补充，不要求现在记录每次出牌时的整个世界状态。

## 5. 具体埋点清单

本节的优先级用于采集排期：**P0-A 是已有信息留存与可靠性；P0-B 是补齐不可恢复的动作事实；P1 是更细机制解释。** P0-B 缺失的时间段只能支持部分分析，不能标记为完整战斗样本。

### 5.1 对局生命周期与房间

**当前位置：** `GameBuddyExporter.EnsureRunLifecycle / InferRunResult / EndActiveRun / PublishTransitions`。

| 建议事件 | 触发时机 | 主要字段 | 优先级 |
| --- | --- | --- | --- |
| `run.observed` | 首次看见一局，包括中途接入 | 当前构筑与资源、首次楼层、是否开局、身份依据 | P0-A |
| `run.started` | 确认新局真正建立 | 初始构筑、角色、进阶、模式、初始资源 | P0-B |
| `run.resumed` | 确认从存档恢复 | 原局身份、恢复位置、是否回退、上个片段 | P0-B |
| `run.suspended` | 确认暂离或存档退出 | 当前位置、可恢复状态、观察依据 | P0-B |
| `run.ended` | 游戏确认结束 | `win/loss/abandoned`、结束原因、最终快照、游戏有效时长及来源 | P0-B |
| `room.entered / room.exited` | 房间实际进入/离开 | 房间实例、节点类型、实际房间类型、生命/金币/物品前后 | P0-A |

不能把“暂时拿不到 RunState”“连接断了”或“进程退出”直接当放弃。只知道观察结束时，记录采集片段关闭，保留结果未知。

时长区分真实游戏时长、可观测时长和墙钟经过时间；当前从首次观察起计时不能直接作为完整对局时长。

### 5.2 奖励候选与选择

**当前位置：** `CardRewardPatches`、`PublishCardRewardIfReady / ClearCardRewardScreen / PublishSelectedCardIfReady`、`GameBuddyRewardSelectionTracker`。

| 建议事件 | 触发时机 | 主要字段 | 优先级 |
| --- | --- | --- | --- |
| `reward.offered` | 一次奖励可见时 | `decisionId`、奖励来源、候选槽位、卡牌详情、可跳过状态、前置快照 | P0-A |
| `reward.updated` | 同次奖励内容刷新 | 同一决策 ID、候选版本、变化原因与新候选 | P0-A |
| `reward.resolved` | 选择结果确认 | `selected/skipped/cancelled/unknown`、候选版本、选中槽位/实例、结果证据 | P0-B |

要求：

- 保留出现过但没有选择的候选，含实际升级状态与运行时变化；不能只记录选中的牌。
- 候选按槽位和实例保留，不按卡牌类型 ID 去重。相同类型的两个候选也可能不同。
- 奖励来源记录实际来源，不能全部写成战斗；战斗来源关联 `combatId`。
- 界面关闭属于生命周期信号，不等于明确跳过。结果延后确认时应留为待解析，超出解析窗口后明确未知。
- 无牌组增量不证明跳过；单一候选增量只能在已知约束下作为 `state_diff` 推断。
- 使用独立 `decisionId`，候选内容签名仅用于识别是否刷新。

### 5.3 永久构筑、遗物与药水变化

**当前位置：** `BuildSnapshot / MapCard / MapCards` 已能提供部分状态；需要在永久变化实际生效处补动作 Hook。

| 建议事件 | 主要字段 | 优先级 |
| --- | --- | --- |
| `deck.card_added / removed` | 卡牌实例、类型、完整已知状态、来源动作、前后构筑快照 | P0-B |
| `deck.card_upgraded / transformed / modified` | 同一实例或新旧实例关系、变化前后、修改类型、来源 | P0-B |
| `relic.gained / lost / changed` | 遗物类型与实例、可影响机制的状态/计数、来源 | 获得/失去 P0-B；状态细分 P1 |
| `potion.gained / used / discarded / replaced` | 药水、槽位、目标、来源、前后槽位状态 | P0-B |

初期尚无可靠 Hook 时，保存构筑变化快照与差分结果，未知来源就记录未知。构筑快照可立即提供价值，但不能宣称捕获了采样间隔内每次变化。

转化要把旧牌和新牌关联为同一个动作，不能只留下无关联的删除与新增。升级也不能只保存是否升级的布尔值；运行时支持的次数、附加效果等应按已核对能力保留。

### 5.4 地图与路线

**当前位置：** `BuildMapSnapshot / ResolveOriginIds / EnumerateRoutes`、`PublishTransitions`。

| 建议事件 | 主要字段 | 优先级 |
| --- | --- | --- |
| `map.observed` | 地图实例、节点、连接、当前节点、玩家已知房间信息、数据完整度 | P0-A |
| `route.offered` | 决策 ID、当前实际合法入口、入口房间类型、当时资源与构筑、可见后续信息 | P0-A；合法性需实机核对 |
| `route.selected` | 同一决策 ID、选中入口、选择确认来源、是否只有一个合法入口 | P0-B |

“整张地图存在精英”“若干步后能到精英”和“当前有可选择的精英入口”是不同事实，不能合并成一个布尔值。

优先保存地图图结构、当时的实际可选入口和玩家已知范围，未来再计算路径属性。现有路径枚举存在数量上限，截断时必须保留 `routesTruncated`，不能把枚举没包含的路线当不可达。

实际合法入口可能受游戏规则影响，不能仅把拓扑子节点永久等同于可点击节点。隐藏信息如果内部可读，也要与当时玩家可见信息分开，避免未来用事后信息评判决策。

### 5.5 商店

**当前位置：** `BuildShopSnapshot / MapShopItem / PublishShopLifecycle`。

| 建议事件 | 主要字段 | 优先级 |
| --- | --- | --- |
| `shop.opened / inventory_updated` | 商店访问 ID、商品实例/槽位、全部已知库存、实时价格、可购买状态、进店金币 | P0-A |
| `shop.transaction_completed` | 交易 ID、商品/服务、数量、实际扣款、交易前后金币、删牌对象、结果物品 | P0-B |
| `shop.closed` | 访问 ID、离店金币、交易完整度、离开原因 | P0-A |

不要把当前数组 `index` 当稳定商品身份：已售出商品从快照过滤后，后续索引会变化。应建立本次访问内稳定的商品实例 ID。

价格标注、可负担状态与实际扣款分别保存。购买失败可另记结果，但不能进入成功消费统计。金币减少不能直接认定为购买，库存消失也不能单独作为成交证明。

如果考虑玩家为什么没有购买某张牌，需要保留未购买库存及当时价格，而不仅是购买记录。

### 5.6 火堆

**当前位置：** `PublishTransitions / InferRestClosed`、`harness/rest-lifecycle.js`。

| 建议事件 | 主要字段 | 优先级 |
| --- | --- | --- |
| `rest.options_offered` | 火堆访问 ID、动作列表、是否可选、禁用原因、生命、构筑、可见后续路线 | P0-B |
| `rest.action_completed` | 访问 ID、实际动作、升级对象、实际回血、其他实际效果、动作前后快照 | P0-B |

以动作完成为权威事实。满血选择回血、已有同名升级牌后再升级另一张、非升级/回血的特殊动作都应可表达。

现有 Mod 与桌面端都包含推断逻辑。过渡期间用访问 ID 和动作关联防止重复计数；保留推断证据，但后续计算应优先使用直接完成事件。

### 5.7 事件与远古选择

**当前位置：** `BuildEventSnapshot / PublishEventLifecycle`，现有事件路径也承接开局远古选择。

| 建议事件 | 主要字段 | 优先级 |
| --- | --- | --- |
| `event.options_offered` | 事件实例、事件类型、页面实例、页面版本、全部选项、稳定选项 ID、锁定状态、当时可见代价/收益 | P0-A |
| `event.option_selected` | 决策 ID、页面版本、选项 ID、选择前状态 | P0-B |
| `event.option_resolved` | 同一动作 ID、实际扣血/金币、得失牌/遗物/药水、进入下一页或战斗、结果完整度 | P0-B |

每次页面出现都需要实例身份。同一个页面定义可能多次访问，不能只用 `eventId + pageId` 作为唯一决策身份。

显示的可能收益与执行后的真实结果分开。随机结果不能提前填入实际收益。若效果已由通用构筑/资源事件记录，解析记录引用对应事件，避免统计两次。

### 5.8 战斗边界和回合

**当前位置：** `BuildSnapshot / PublishTransitions / MapEnemy`。

| 建议事件 | 主要字段 | 优先级 |
| --- | --- | --- |
| `combat.started` | 战斗 ID、遭遇 ID、实际战斗类型、敌人类型与实例、初始生命、战前构筑/遗物/药水/资源 | P0-B；先留观察快照 P0-A |
| `turn.started / turn.ended` | 战斗 ID、轮次、行动方、阶段、生命/格挡/资源/状态、手牌和牌堆快照 | P0-B |
| `combat.ended` | 明确胜负、终止原因、战后快照、完成的回合、数据覆盖 | P0-B |
| `entity.spawned / exited` | 实例、类型、初始状态、生成来源、死亡/逃离/移除原因 | P0-B |

“轮次”和“玩家行动回合”不能默认为完全相同概念。多人或其他行动主体要能记录 `actorId / phase`，即便第一批分析只筛选单人。

怪物类型 ID 不是实例 ID；两只同种敌人必须分别记录。当前快照只列活着的可攻击敌人，不能依赖它补回致死结算。

### 5.9 出牌、伤害与机制结算

**当前位置：** 协议已有 `card.played`；实际游戏 Hook 未接入。`TrackTurnDamage` 仅为生命差估计。

| 建议事件 | 核心字段 | 优先级 |
| --- | --- | --- |
| `card.played` | 卡牌实例/类型、升级与临时状态、行动方、目标、主动/自动、实际支付资源、动作 ID | P0-B |
| `damage.resolved` | 来源动作/实体/效果、目标实例、结算伤害、格挡吸收、实际生命损失、是否自损、前后状态 | P0-B |
| `block.changed` | 目标、前后格挡、变化量、获得/吸收/过期/其他原因、来源 | P0-B |
| `heal.resolved` | 目标、请求治疗量（可得时）、实际恢复量、前后生命、来源 | P0-B |
| `resource.changed` | 玩家/实体、资源类型、前后值、变化量、获得/支付/重置原因、来源 | P0-B |
| `card.drawn / discarded / exhausted / generated` | 卡牌实例、起止区域、来源动作、永久牌关联、动作顺序 | P0-B 基础事件 |
| `power.changed` | 目标、效果类型、变化前后层数、来源动作 | P0-B |
| `mechanic.triggered` | 经核对的机制 ID、触发来源、关联输入与输出事件 | P1 |

#### 结算口径

- 展示伤害、结算伤害、实际生命损失不混用；未知字段保持未知。
- 挡住伤害和获得格挡不是同一个数。格挡过期也不是吸收了伤害。
- 主动自损与敌人造成的生命损失分开；药水、遗物、持续效果伤害保留来源类别。
- 治疗记录实际恢复；满血时尝试治疗和真正恢复要能区分。
- 多段伤害分别记录，使用动作 ID 聚合；对多个目标的效果按实例拆分。
- 消耗记录发生的次数与来源；消耗后移回并再次消耗可以产生多次合法事件。
- 卡牌面板费用不等于实际支付费用；X 费、减费和额外资源都记录实际结算。
- 卡牌生成、入手与抽牌区分；暂时未抽到手的生成牌也应有生成事实。
- 卡牌自动触发与玩家手动打出区分，避免自动机制扭曲个人出牌倾向。

同一次伤害既可能有生命变化记录，也有伤害结算记录；必须用动作/结算身份关联。未来聚合从指定权威事件计算，不能把两类事件相加。

#### 因果关联的最低要求

例如一次消耗引发抽牌和格挡，应留下“消耗事件 → 被触发效果 → 抽牌/格挡结算”的关联；不能仅因它们时间接近就认定同源。

若游戏接口无法提供完整因果链，至少保存来源类型和来源实体，并标注无法归因。第一版不要求完成所有机制的解释，但不能伪造因果。

### 5.10 全局资源变化：战斗之外也要采

生命、最大生命、金币和容量变化不只发生在战斗。建议通用资源事件在所有房间生效，避免商店、事件和奖励各自记录不一致的局部统计。

| 建议事件 | 核心字段 | 优先级 |
| --- | --- | --- |
| `gold.changed` | 前后金币、实际变化量、获得/花费/损失原因、来源动作 | P0-B |
| `health.changed` | 前后生命、变化量、治疗/伤害/设置/其他原因、关联结算事件 | P0-B |
| `max_health.changed` | 前后最大生命、变化量、原因、同时发生的当前生命变化引用 | P0-B |
| `capacity.changed` | 容量类型、前后值、来源；例如目标构建支持的药水槽位容量 | P1；现有可读状态先保留 |

最大生命下降导致当前生命变化，不能自动当成敌人伤害；事件代价、商店支付和战斗内资源消耗必须保留不同来源。战斗中 `damage.resolved` 与 `health.changed` 可以共同作为核对证据，但同一生命损失不能累计两次。

金币净变化也不等于交易实际价格。例如同一动作产生扣款与返还时，应分别记录结算或明确拆分实际支付和返还，未来消费口径再选择如何计算。

## 6. 《杀戮尖塔 2》适配要求

以下要求基于当前项目的 STS2 接入方式制定，不假设一代的 Mod API 或机制一定适用。

### 6.1 Hook 必须核对目标构建

当前已明确的 Harmony 补丁是奖励界面的打开、刷新和关闭。出牌、伤害、交易、事件选择和永久牌组变化的准确游戏内部方法，仍需对照目标构建的 `sts2.dll` 核对。

每个新增 Hook 实施前登记：目标构建、类型/方法签名、同步或异步、参数与结果含义、调用次数、是否覆盖自动触发、失败或取消路径。异步方法的返回不一定等于效果已经结算，需验证真正完成点。

补丁失败时上报能力不可用，不能静默输出“该局没有出牌/没有受伤”。轮询回退只能标记为估计或部分覆盖。

### 6.2 角色资源与实体

当前 `MapCard` 已读能量费用及星费信息，但 `PlayerSnapshot` 没有对应的完整星资源状态。资源事件建议使用 `resourceId + amount` 的可扩展模型，覆盖目标构建实际支持的资源；没有数据时不得把未知转换为 0。

`power.changed` 使用效果 ID 与层数记录，避免只围绕铁甲的力量写死。实际存在的其他战斗实体也应可表达所有者、类型和实例身份，具体支持范围由运行时核对决定。

### 6.3 多人和观察主体

当前采集通过 `LocalContext.GetMe(runState)` 选择本地玩家，失败时回退到首个玩家。埋点必须保存玩家槽位、玩家数量和主体识别依据；身份未知时不能悄悄将首个玩家当本地玩家。

若暂不支持多人分析，照样记录模式与不支持原因，未来筛除即可。共享敌人的掉血不能默认全部归因于本地玩家。

### 6.4 版本与卡牌状态

当前卡牌主要有类型 ID、升级布尔值、文本与费用。应保留目标构建实际暴露的永久修改、附加效果、临时费用等结构化状态，并用能力清单说明支持哪些字段。

运行时文本可作为版本核对证据，按内容去重保存；不应每条伤害重复附带完整描述，也不能只靠中文名称匹配实体。

## 7. 埋点写到哪里，怎样防止丢失

### 7.1 职责分工

| 层 | 职责 | 当前接入位置 |
| --- | --- | --- |
| Mod 生产者 | 在事实发生处采集、分配身份与序号、关联上下文、缓冲待确认事件 | `GameBuddyExporter` 与新增的经验证 Hook |
| 协议边界 | 校验信封和事件载荷，识别版本与能力 | `harness/protocol.js` |
| 桌面端记录器 | 去重、持久化、确认、检测缺口、保存关键快照 | `main.js::connectBridge` 消息处理处，独立记录模块 |
| 功能消费者 | 消费已经确认的事实；以后计算个人数据、复盘和战斗分 | `review/service.js` 等 |
| 调试工具 | 导出与重放相同事实契约 | `harness/record-bridge.js` 与 Replay |

新增记录器应位于消息校验之后、UI 装饰和业务聚合之前。不能在 `publishReviewChanged`、页面打开或 LLM 完成时才记录游戏事实。

快照采样和事件记录分开：高频重复状态可以压缩，合法事件不能因为内容相同而删除。对新增事件同步扩展协议白名单，否则 Mod 已发送也会被桌面端拒收。

### 7.2 建议本地文件组织

使用安装版应用数据目录，避免当前工作目录受启动位置影响。以下为建议布局，不代表现有文件已创建：

```text
userData/facts/v1/
  runs/<runId>/
    manifest.json
    events-0001.jsonl
    snapshots-0001.jsonl
    coverage.json
  catalogs/<catalogHash>.json
  index.json
```

- `manifest`：对局身份、环境版本、观察片段、文件引用。
- `events`：追加事实记录，不在每次事件时重写整局。
- `snapshots`：关键状态，按 ID 引用，可分块压缩。
- `coverage`：各事件族覆盖区间、能力、缺口和异常。
- `catalogs`：解释旧版本实体所需的目录内容。
- `index`：可重建检索索引，不是原始事实的唯一来源。

后续若需要更强查询能力可以迁移存储，事件语义和身份应保持稳定。不要把未来个人数据“最近 50 局”的展示窗口当成原始数据保留上限。

### 7.3 可靠发送与落盘

1. Mod 产生事件时立即分配 ID/序号，并放入独立于 UI 的发送队列。
2. 桌面端校验后按 ID 去重并批量追加；关键生命周期/决策边界及时提交。
3. 持久提交后才返回该源流的连续确认序号；只收到内存中不能确认已保存。
4. 重连时从确认位置重发。发送保持单一有序队列，避免独立异步发送打乱源顺序。
5. 源队列溢出或无法补发时，保存明确的缺失序号范围与原因。
6. 桌面端重启扫描末尾，处理未写完整尾行并记录恢复情况，不悄悄吞掉损坏片段。
7. 采集队列、写盘或协议错误不得阻塞游戏主线程；通过质量事件暴露失败。

仅有 Mod 内存队列能覆盖短断线，不能保证游戏崩溃或桌面端长时间未启动时不丢数据。若目标包含“桌面端不运行也采集”，必须另行实现 Mod 本地持久缓冲；否则明确记录观察范围。本方案最低范围是 Bridge 与桌面端记录器运行期间的可靠采集。

批次大小、刷新周期、队列容量和总磁盘上限先作为可配置参数，通过真实对局测量再定。记录器必须统计写盘延迟、队列深度、丢弃量和文件体积，不凭假设承诺固定开销。

### 7.4 完整度与观测健康

建议补充 `capture.started / capability_reported / gap_detected / recovered / stopped` 等记录。

每个事件族保存：是否支持、何时开始/停止、是否存在缺口、捕获/拒收/重放数量、观察或推断方式。不能只设一个全局 `complete=true`。

例如某局可以同时具有：构筑时间线完整、奖励结果部分未知、战斗伤害不支持。未来各功能按自己的要求筛选。

“没观察到伤害事件”可能是没受伤，也可能是 Hook 未工作。只有能力正常且对应区间完整时，零事件才可解释为零次发生。

## 8. 现在采事实，以后再计算哪些指标

| 未来结果 | 可由哪些事实计算 | 额外约束 |
| --- | --- | --- |
| 攻击牌使用比例 | `card.played` | 区分主动/自动；类型未知不进入已知分母 |
| 奖励跳过比例 | `reward.offered + resolved` | 只纳入结果明确、具有跳过机会的决策 |
| 主动挑战精英倾向 | `route.offered + selected`、实际房间 | 对可选机会建立分母，不用精英场数替代选择机会 |
| 商店消费与购买结构 | 库存、成交、进出店金币 | 成交完整才能认定“没有消费” |
| 火堆升级倾向 | 动作候选与完成事件 | 区分无法升级、没有可升级对象等情况 |
| 四流派分、峰值、首次达标 | 构筑/遗物时间线、对应版本知识库 | 固定同一计算版本；缺中间记录不能声称准确首次时间 |
| 流派实战触发情况 | 出牌、效果、来源链和战斗区间 | 未归因不冒充机制贡献 |
| 总伤害、承伤、治疗、最高单回合伤害 | 结算事件与回合边界 | 统一口径；截断回合不计算精确峰值 |
| 生存相关选择 | 决策前资源、候选、选择和近期战斗 | 可以描述低血量时选择，不能直接证明玩家动机 |
| 战斗分实验 | 环境、战前状态、过程与战后结果 | 公式未定前不删细节；客户端事实不等于竞技防作弊证明 |

暂时不必为了未来功能新增“流派成型了”“玩家很克制”“这场战斗 90 分”等事实事件。这些是可变解释，不应替代基础记录。

若希望评估现有建议与选择是否一致，可以额外记录：`recommendationId`、关联 `decisionId`、规则/模型版本、结构化推荐项、真实展示时点、最终游戏选择。无需保存提示词和模型全文；发送到 renderer 也不自动等于用户看到了建议。该组属于可选扩展，优先级低于游戏事实闭环。

## 9. 本地保留、团队研究与远端边界

### 9.1 本地原始事实

保存支持复盘所需的构筑、候选、逐动作记录和版本。按大小或保留期清理时，记录哪些局已被裁剪，提供可导出的研究样本；不能继续将裁剪后的局标为完整。

运行时个人数据、未来排行榜、研究样本和一般产品遥测是不同数据用途，不复用含义不清的“所有埋点上传”开关。

### 9.2 团队怎样拿到可分析数据

默认本地存储只能支持玩家本机的后续功能。团队想校准流派规则、验证指标或排查采集，需要显式的样本导出/提交路径。

建议在内测中使用经过用户授权的样本包，至少包含版本、所需事件、快照、目录与覆盖报告；可以先手动导出，不要求本次建设云服务。跨局长期趋势若需要身份关联，另用明确用途的随机研究标识，不使用设备或账号标识，也不冒用局 ID。

如果只能上传计数与分数桶，就只能回答对应的聚合问题，不能日后重建构筑时间线或任意重算战斗公式。上传契约应从研究问题反推，不能宣称“先存几个总数，以后什么都能做”。

### 9.3 不进入事实记录的内容

- API Key、授权头、LLM 提示词和模型原始输出。
- 玩家真实姓名、平台账号、设备标识、本地绝对路径。
- 原始 seed；如确需本机匹配线索，遵循既有本地边界且不充当唯一身份。
- 每帧完整游戏状态和无目的的任意对象转储。

导出和未来上传采用白名单，不直接把调试日志、异常原文或 `decisions.jsonl` 当成研究数据包发送。

## 10. 建议实施批次与交付物

### 批次 A：已有数据先留住（P0-A）

**工作：**

- 定义事件信封、对局/片段/决策身份和版本字段。
- 增加独立持久记录器、源端序号、去重、缺口报告。
- 保存已有奖励候选、地图、商店库存、事件选项和关键状态。
- 保留能力清单，中途接入和推断来源明确标记。
- 修改调试录制/回放契约，使其能够验证事实记录，而不按内容删除合法重复事件。

**交付物：** 事件字典、字段校验、一个可检查的真实局样本包、覆盖报告。

**能力边界：** 可以分析已捕获候选和构筑快照；还不能宣称获得精确跳过率、逐笔消费、出牌率或战斗分输入。

### 批次 B：选择闭环（P0-B）

**工作：**

- 奖励明确拿取/跳过/取消结果。
- 商店成交与删牌、火堆动作、事件选择及效果。
- 路线实际可选入口与确认选择。
- 永久牌组、遗物、药水变化与来源。
- 经验证的开局、读档、结束身份与结果。

**交付物：** 每个决策族都能联查“候选 → 选择 → 结果”；不能解析的选择有未知记录。

### 批次 C：战斗事实闭环（P0-B）

**工作：**

- 经目标 STS2 构建验证的出牌和结算 Hook。
- 战斗、回合、敌人实例身份和准确结束结果。
- 伤害、格挡、治疗、资源、抽牌、消耗、生成牌、状态变化。
- 战前/战后与回合边界快照、基础来源关联。

**交付物：** 可以逐事件核对的战斗样本；出牌次数、生命变化和战斗结果可与实机对照。

批次 B 和 C 都是值得尽早完成的不可恢复数据采集。若开发资源有限，先保证 A，再按“决策复盘”和“战斗分析”的近期研究需求安排 B/C，不能只做 A 却声称已为全部未来功能收齐数据。

### 批次 D：细机制与研究增强（P1）

- 更完整的触发链、角色专属资源与实体。
- 建议真实展示与选择关联。
- 经过授权的研究样本导出及抽样策略。
- 根据已测体积和性能确定保留与压缩策略。

本次文档不修改业务行为。实际实施会改变 Mod 采集与事件协议，必须按仓库 `AGENTS.md` 先走 OpenSpec，存在对应 `tasks.md` 后再改业务代码。

## 11. 验收场景

### 11.1 功能事实验收

| 场景 | 必须观察到的正确记录 |
| --- | --- |
| 正常从开局到结束 | 同一对局身份、真实初始状态、明确结束结果、可定位的观察范围 |
| 中途才启动桌面端 | 首次观察而非伪造开局；此前区间明确未覆盖 |
| 退出再读档 | 已确认恢复时关联原局；不能把暂离直接判放弃 |
| 同角色同 seed 新开 | 新尝试身份，不覆盖上一局 |
| 读档回退并重打战斗 | 新片段/战斗尝试关系明确，不把两次动作拼成同一场 |
| 奖励选牌、跳过、取消 | 三者能区分；失败路径落为未知而不是默认为跳过 |
| 同一候选组合再次出现 | 不同决策 ID；同次刷新只变候选版本 |
| 升级第二张同名牌 | 具体实例可识别，不因已有同名升级牌而漏记 |
| 商店连续购买再删牌 | 每笔商品身份、实际扣款、删除对象清楚，索引变化不串单 |
| 火堆可升级与不可升级 | 候选限制留存；统计分母可区分 |
| 多页面或随机事件 | 页面实例、选择和实际结果关联；可能收益不冒充实际收益 |
| 路线被迫经过精英 | 有且仅有一个合法入口时可识别，不误算主动挑战 |
| 一次动作多段/多目标伤害 | 分次记录、统一动作关联、目标实例独立 |
| 同种敌人同时存在、死亡或召唤 | 实例不混淆；致死、生成、移除可核对 |
| 同一回合先掉血再回血 | 承伤与治疗独立，不被净血量差抵消 |
| 主动自损与敌人伤害 | 来源区分，不混算为同一种承伤 |
| 自动出牌与手动出牌 | 模式区分；重复打出同名牌仍各有事件 |
| 消耗触发抽牌和格挡 | 来源可关联；不能归因时明确未知 |
| X 费/额外资源支付 | 保存实际支付量，不能只读面板费用 |

### 11.2 可靠性验收

| 场景 | 必须达到的结果 |
| --- | --- |
| 同一事件补发多次 | 原始事件只入库一次，确认可重试 |
| 连续两个完全同内容的合法动作 | 保留两条不同 ID 的事件 |
| 接收超过 100 条事件 | 历史事实不因观察缓存上限而消失 |
| 短断线恢复 | 能补发则补发，不能补发则明确缺口范围 |
| 源进程重启 | 新源会话身份；序号重置不撞历史事件 |
| 桌面端写盘失败/磁盘满 | 不确认未持久化记录；有失败状态，不阻塞游戏 |
| 写入过程中崩溃 | 已确认持久部分可恢复；损坏尾部有报告 |
| Hook 未挂上或版本不兼容 | 对应事件族标记不可用，不能报告完整且全零 |
| 游戏事实与推断事件同时到达 | 原始证据可留存，业务计数按关联去重 |
| 回放导入 | 保持原事件身份及源信息；标记回放，和实机采集区分 |

### 11.3 核对方式

- **实机对照：** 人工标记关键动作或录制测试视频，与事件逐项核对。视频不是常规玩家埋点内容。
- **资源核对：** 在规则适用且区间完整时检查金币、生命、牌组和资源的前后变化；最大生命变化、死亡、复活及特殊机制需单独处理，不能硬套简单守恒式。
- **回放校验：** 同一事实文件反复导入产生相同摘要；重复传输不改变计数。
- **边界检查：** 每次已结束决策有明确或未知结果；每场战斗有开始/结束或缺失说明。
- **性能测量：** 长战斗、连续自动触发和大量事件时检查游戏主线程、队列、写盘和文件大小。

验证要求不是“跑几局没报错”，而是覆盖上述事件语义和故障路径。协议/单元测试只能验证约定，不能替代目标游戏构建的 Hook 实机验证。

## 12. 数据采起来之后，首先做哪些检查

不必等未来功能做完，就可以先产出以下数据质量报告：

1. 每类 Hook 的实际覆盖版本、成功启用率和缺失区间。
2. 有完整候选的决策数、结果明确数、未知数及未知原因。
3. 有完整初始状态和结束结果的对局数，中途接入与读档回退比例。
4. 战斗出牌/结算覆盖率、来源可归因比例、前后状态无法对账的场次。
5. 各角色、进阶、模式、版本和遭遇的有效样本数。
6. 每局事件量、文件体积、写盘耗时、重传量、拒收量和丢失量。

有了质量报告再判断能否研究：先筛选证据完整的样本，再比较构筑变化、候选选择和后续表现。各类分析的有效样本数不同，不能用“总共收了多少局”代替。
